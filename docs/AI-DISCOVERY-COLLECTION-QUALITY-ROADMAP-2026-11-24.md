# AI 搜索、智能推荐、自动采集与内容质量治理升级路线

> 状态：实施设计基线（2026-11-24）
> 适用项目：山羊胡网（NavHub）
> 原则：增量增强现有能力，不重写检索引擎、不改变现有数据事实源、不自动删除或自动发布未经验证的外部内容。

## 1. 本轮代码审查确认的现状

本文件依据当前 `main` 分支的下列实现审查形成；它是针对关键链路的代码审查，不代表已完成全仓库安全审计。

| 能力 | 已存在的实现 | 本轮需要继续解决的问题 |
|---|---|---|
| AI 智能搜索 | `packages/store/src/search.ts` 有 exact / FTS / 拼音 / semantic 多通道、RRF、语义相似度闸门、LinUCB 自适应调权；`apps/api/src/routes/search.ts` 负责身份可信度、个性化画像、事件和缓存隔离；`packages/core/test/search-eval-golden.test.ts` 已有生产融合逻辑金标回放，当前 fixture 为 9 条查询 | 已有离线评测底座，不应重复建设；需要扩大查询类型覆盖、用真实召回快照替代/补充手工快照，并补线上分桶指标和失败查询闭环；搜索“有结果”不等于结果“相关、可信、可用” |

| 自动采集与富化 | `apps/api/src/routes/enrich.ts` 提供 URL 富化和自动入库；`packages/ai/src/enrich.ts` 负责安全抓取、元数据抽取和可选 LLM 富化；`metadata-refetch.task.ts` 支持元数据刷新 | 自动入库前需要更严格的候选预检、证据留存、字段级置信度和重复检测；抓取失败或模型降级必须可见，不能生成“看似完整”的虚假元数据 |
| 站点健康 | `health-check.task.ts` 已有分层探活、软 404 / 停靠页识别、连续失败阈值、WAF 阻断保护 | “可访问”不代表“内容质量好”；健康、内容质量、政策合规必须分开评分 |
| 内容治理 | `packages/core/src/taxonomy-governance.ts` 和对应 store repository 已有分类/标签治理提案；采集和富化已有来源信息 | 需要建立跨站点质量评分、重复/镜像识别、过期检测、风险标记和人工审核状态机，且所有自动治理动作可审计、可回滚 |

## 2. 总体目标与产品边界

建立一条可观测、可评估、可纠错的资源发现闭环：

1. 用户表达任务或问题；
2. 搜索理解查询意图，混合召回候选；
3. 质量与安全规则过滤明显不合格内容；
4. 排序综合相关性、质量、时效、可信度和用户偏好；
5. 结果点击、收藏、停留、跳过、举报和零结果反馈形成弱监督信号；
6. 采集系统持续发现候选、抓取证据、富化字段、检测重复；
7. 质量治理把异常条目送入复核队列，人工裁决后再发布、合并、降权或归档；
8. 离线评测与线上指标验证每次算法变更。

**不允许的行为：**
- LLM 不得自行创造站点、URL、价格、功能、排名或“官方认证”等事实。
- 未经人工确认，不自动删除站点、不把第三方候选直接公开发布、不覆盖高置信度人工维护字段。
- 不把用户原始搜索、收藏或个人行为上传给外部模型作为训练数据。
- 不因一次超时、403、429 或单次抓取失败就判定站点失效。
- 不把 HTTP 200 等同于站点真实可用或内容优质。

## 3. 目标架构

### 3.1 搜索与排序

建议采用“多路召回 → 安全/质量过滤 → 特征重排 → 结果解释 → 反馈学习”分层结构：

- **意图解析**：识别任务型、导航型、比较型、教程型、品牌/产品型、中文拼音型查询；解析语言、实体、时间约束与筛选条件。解析失败时原样走现有检索，不阻断搜索。
- **候选召回**：保留现有 exact、FTS、pinyin、semantic、personal 五路机制及现有降级路径；新增通道必须能单独开关、计时和评测。
- **硬过滤**：排除已删除、未发布、明确恶意、确认失效、重复且被合并的记录；WAF/机器人拦截只标记“无法验证”，不能当成失效。
- **重排特征**：文本相关性、多通道共识、语义相似度、站点质量、可用性置信度、最近验证时间、用户偏好、地域/语言适配、结果多样性。
- **结果解释**：说明“为什么推荐”，只引用站点已有字段和可验证信号；推荐理由不可声称模型未验证的功能。
- **反馈闭环**：记录匿名化/受控的曝光、点击、收藏、快速返回、长停留、隐藏和举报事件；尊重用户的个性化、遥测与历史开关。

### 3.2 推荐系统

推荐分为四种明确场景，不共用一个未经区分的“猜你喜欢”排序：

1. **首页发现**：质量优先、兴趣适配、类目多样性和新站探索之间平衡。
2. **站点详情页相似推荐**：语义相似 + 类目/标签重合 + 生态关系；排除自身、镜像重复和低质量候选。
3. **任务型 AI 找站**：先理解用户任务，再按任务步骤召回；每一步候选必须来自目录真实记录。
4. **新站/冷启动推荐**：使用类目、语言、描述、人工标签等内容特征，不依赖用户行为数量。

推荐结果需要提供多样性约束：同一品牌/同一域名族/同一功能的候选不能占满首屏；保留少量高质量探索位，避免热门站点形成永久垄断。

### 3.3 自动采集流水线

建议将采集拆成可重试、可观测的阶段：

`发现候选 → URL 规范化 → SSRF/协议校验 → 域名与重复预检 → 安全抓取 → 元数据抽取 → 字段置信度 → 质量评分 → 人工/自动分流 → 入库 → 搜索/向量索引 → 定期复检`

每阶段记录任务 ID、来源、时间、耗时、结果状态、错误类型和重试次数。采集来源至少区分人工投稿、管理员导入、官方目录/公开 API、公开网页发现和用户提交。保留原始证据摘要与字段来源，不长期保存不必要的整页正文。

**调度要求：**
- 有界并发、每域名速率限制、全局抓取预算和协作式取消。
- 失败退避与死信/人工复核队列；同一 URL 幂等。
- 每次任务有最大运行时间、最大响应字节数、最大重定向数和内容类型限制。
- 遵守 robots.txt、站点服务条款和适用法律；不绕过登录、验证码、付费墙或访问控制。
- 对外链抓取沿用 SSRF 防护，重定向每一跳重新校验 DNS/IP，拒绝私网、环回、链路本地和云元数据地址。

### 3.4 内容质量治理

质量分数用于排序和审核分流，不直接替代发布状态。建议保留可解释子分：

| 子分 | 主要证据 |
|---|---|
| 可访问性 | 多次探活结果、终态 URL、软 404/停靠页识别、验证时间 |
| 内容完整度 | 标题、描述、语言、图标、类别、标签字段质量 |
| 信息可信度 | 官方来源证据、域名一致性、来源类型、字段 provenance |
| 相关性 | 类目/标签与站点内容是否一致，用户搜索相关反馈 |
| 独特性 | URL 规范化、域名族、内容指纹、语义近重复 |
| 时效性 | 最近验证时间、页面变更信号、产品是否仍维护 |
| 风险 | 恶意跳转、仿冒、垃圾 SEO、诱导下载、违规或不安全内容 |

每个维度必须能输出 `score + evidence + evaluatedAt + version`。缺失证据应标为“未知”，不得自动按 0 分或满分处理。总分模型需版本化，避免评分公式升级后无法解释历史变化。

## 4. 分阶段实施计划

### P0：建立可量化基线（先做）

- 整理搜索金标集：中文口语、英文、拼音首字母、错别字、任务型查询、品牌词、零结果和低相关噪声查询。
- 对每条查询标注 0–3 级相关性；固定评测数据版本。
- 输出 NDCG@10、MRR@10、Recall@20、零结果率、首屏低质率、搜索 P50/P95 延迟和 semantic 降级率。
- 以当前线上排序作为 baseline；任何重排调整先跑离线对比，禁止只凭主观体验上线。
- 盘点曝光/点击/收藏/停留/快速返回/隐藏/举报事件是否完整、可删除、可关闭，并检查身份隔离与缓存 Vary。

**验收：** 现有 9 条样本继续作为回归基线；新增样本有来源、采样时间和人工标注依据；真实召回评测与合成排序测试分开报告；每次算法 PR 都能比较新旧指标；无数据时明确报告样本不足，不伪造提升百分比。

### P1：质量感知的搜索重排

- 在现有 RRF 结果之后增加可配置的轻量重排层；先只消费已存在、可信的质量字段。
- 引入站点状态、最近验证时间、字段完整度、人工精选标记、域名重复族和用户偏好。
- 先以 shadow mode 记录新旧排序差异，不影响用户结果；验证稳定后再按小流量启用。
- 增加多样性与同域名族去重规则；保留“为什么出现该结果”的调试信息。
- 保留现有 semantic unavailable / keyword fallback，不允许新层让搜索因模型不可用而失败。

**验收：** 相关性指标不低于 baseline 的预设容忍范围；P95 延迟增加受控；所有硬过滤有测试；可以一键关闭新重排。

### P2：推荐统一与反馈治理

- 统一首页、相似站点、场景包、AI 找站的候选质量特征与解释结构，但保留各场景不同的目标函数。
- 加入冷启动、多样性、频控和新站探索策略。
- 明确协同信号最小群体阈值，防止少量用户行为反推出个体偏好。
- 推荐反馈支持“不感兴趣/重复/失效/不安全/不相关”，进入审核或排序反馈，不直接触发自动删除。

**验收：** 推荐可解释、可屏蔽、可关闭个性化；不出现同一域名族刷屏；冷启动有稳定结果。

### P3：采集队列与来源可信度

- 将现有 `/api/enrich` 与 `/api/sites/auto` 的同步路径逐步抽象为可追踪采集任务；保持原 API 兼容。
- 先增加预检、规范化、重复检测、来源记录和字段级 provenance，再逐步接入后台队列。
- 候选站点默认进入待审核；管理员/可信来源可配置白名单策略，但不能仅凭 LLM 置信度自动公开发布。
- 定时刷新只更新缺失或确实过期字段；人工编辑字段需要锁定/版本冲突保护。
- 对 robots、速率限制、超时、WAF、DNS、TLS、内容类型错误分别分类统计。

**验收：** 重试幂等；并发不重复入库；抓取预算可控；人工字段不会被覆盖；所有候选可追溯来源和处理状态。

### P4：质量治理工作台与自动化复检

- 质量分层：自动通过（仅可信、低风险、规则明确的更新）、人工复核、隔离观察、确认下架。
- 提供重复合并建议、类目错配建议、过期字段刷新、死链复核和风险举报队列。
- 所有治理提案采用 pending / approved / rejected / applied / rolled_back 状态机，并记录操作者、证据、评分版本和前后差异。
- 自动化只提出建议或执行可逆、低风险的动作；删除、合并主记录、封禁域名等高影响动作必须人工批准。

**验收：** 每次变更有审计记录；可以回滚；误报不导致内容永久丢失；治理队列有 SLA 与积压指标。

## 5. 指标字典（第一版）

| 领域 | 指标 | 解释 |
|---|---|---|
| 搜索 | NDCG@10 / MRR@10 / Recall@20 | 金标相关性、首个相关结果位置、相关结果召回覆盖 |
| 搜索 | Zero-result rate | 非空有效查询中无结果的比例 |
| 搜索 | Semantic degraded rate | 预期语义但实际降级为词法的比例 |
| 搜索 | P50 / P95 latency | 端到端搜索延迟 |
| 推荐 | CTR / save rate / hide rate | 点击、收藏和隐藏反馈；必须结合曝光分母 |
| 推荐 | Diversity@10 | Top 10 的类目/域名族多样性 |
| 采集 | candidate acceptance rate | 候选经审核后通过比例 |
| 采集 | duplicate rate | 候选中重复 URL/域名族/内容的比例 |
| 采集 | fetch success / retry / timeout | 抓取成功、重试、超时分布 |
| 治理 | stale-content rate | 超过复检期限且证据不足的条目比例 |
| 治理 | false-positive rate | 人工复核后确认误报的比例 |
| 治理 | review backlog age | 待审核队列积压时长 |

指标必须按查询类型、语言、站点来源、设备/入口分层查看，避免总体均值掩盖中文、英文或移动端体验退化。CTR 不能单独作为质量指标，避免热门偏差和位置偏差。

## 6. 工程实施纪律

- 每个阶段独立 PR；先测试、后灰度、再扩量。
- 新功能配置开关默认保守；模型不可用、向量索引缺失、外部源限流时均有确定性降级。
- 对搜索排序、质量评分、采集规则分别版本化。
- 为新规则添加单元测试、双数据库集成测试、API 契约测试和必要的 Playwright E2E。
- SQLite 与 PostgreSQL 双方言都必须验证。
- 对抓取器执行 SSRF、重定向、DNS 重绑定、HTML 超大响应、压缩炸弹、恶意提示注入和不可信元数据测试。
- 任何模型输入都把网页内容当作不可信数据；网页中的指令不得覆盖系统提示或工具权限。
- 不收集不必要的个人信息；提供数据导出/删除/关闭个性化的能力。

## 7. 下一批具体开发顺序

1. **先扩充现有搜索金标评测**：复用 `packages/core/src/search-eval.ts`、`packages/core/test/search-eval-golden.test.ts` 和 `scripts/search-eval.mts`；补真实查询样本、语料版本、采样来源和线上指标，不重复造轮子。
2. **再做质量特征契约**：确定站点质量子分、证据结构、来源与更新时间字段，先只读计算，不直接改变排序。
3. **再接入 shadow rerank**：对照旧 RRF 输出记录差异，观察 NDCG、延迟和低质首屏率。
4. **再升级自动采集预检**：统一 URL 规范化、重复检测、来源 provenance、字段锁定和候选状态机。
5. **最后扩展推荐与治理工作台**：依赖前面稳定的质量特征和反馈数据，避免先做 UI、后补数据契约。

## 8. 当前明确不做的事情

- 不替换现有五路检索，不移除拼音和关键词降级。
- 不一次性引入大型外部向量数据库、消息队列或 Redis；先基于现有 SQLite/PostgreSQL 与任务系统评估瓶颈。
- 不把所有推荐都交给 LLM 排序；LLM 负责意图理解和受约束解释，确定性排序负责稳定、可评估和可复现。
- 不以“自动采集数量”作为唯一增长指标；更关注有效收录率、重复率、可访问率和审核误报率。
