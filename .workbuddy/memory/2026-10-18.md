### 真问题：通道耗时归因失真（已修）
旧 `runChannels` 把三段并行 `await` 的批次时间**同值**写进 `ftsMs/pinyinMs/semanticMs`——Prometheus 上 fts/pinyin 均值永远等于语义推理时间，通道画像完全失真（实测 7/7/7ms）。

修复（`packages/store/src/search.ts`）：
- 用 `timed()` 包裹每个并行通道，按**各通道自身墙钟**计量（区间可重叠，和为并行口径，端到端以 `tookMs` 为准；注释写清口径）。
- `ChannelTimings` / core `types.ts` 注释同步口径说明。
- `recordSearchChannels(timings, decision)`：planner 决策由 `search()` 的真实结果传入（`result.planner === "early-exit"`），**不再从 `skippedSemantic` 反推**——显式 `disableSemantic` 的请求语义没跑但不是 planner 剪枝，否则 `early_exit` 计数虚高。

实测对照（`/api/metrics`，注意是 **`/api/metrics` 不是 `/metrics`**）：
- 修复前：`channel_avg_ms` fts=pinyin=semantic（同一批次值）。
- 修复后：`exact 1.5 / fts 4 / pinyin 3.5 / semantic 285`；`q=com` 触发 early-exit 后 `planner_total{decision="early_exit"} 1`、`semantic_skipped 1`。

测试：`store.test.ts` 新增「慢 embed（40ms）下 semanticMs ≥ 30 且 fts/pinyin < 30」归因回归；`upgrade-batch1.test.ts` 补显式禁用语义 ≠ planner 剪枝的断言。

## 第二轮：favicon 黑名单在存储层还有两个绕过口（已修）

上轮端到端发现 `/` 的 RSC payload 里仍有 49 处 icon.horse（渲染层已拦住、浏览器 0 请求，但数据层没净化）。根因：`packages/core` 的 `resolveSiteIcon(url, title, customIcon)` **第三参**才带第三方图标服务黑名单，而 `apps/api/src/storage.ts` 两处用的是短路写法 `iconKey || resolveSiteIcon(url, title)` —— iconKey 非空时黑名单完全不生效：

- 读路径 `buildNavigationData.toItem`：脏 iconKey 原样进 navigation.json → RSC payload（本次实证 49 处）。
- 写路径 `upsertSite`：前端后台「读快照 → 保存」的回流会把 icon.horse 再写回库（脏数据自我延续）。

修法（沿用「第三方图标服务 = 视同没有自定义图标」既定策略）：
- core 导出 `isThirdPartyIconUrl`（原内部 `isThirdPartyIcon` 改名导出），供存储层与其它写入点复用。
- `storage.ts` 两处改为把自定义图标作为第三参传入；`seed.ts` 同族写法一并收口。
- 保留 REST `/api/sites` 的原始 iconKey 输出（管理端要看/改存量值；渲染层与快照层已是净化面）。

## 第四轮：快照层三个真缺陷（>100 截断 / 停用类目硬删 / 不可见记录误删）

顺着 storage.ts 深读发现「快照读写必须严格互逆」这条不变量被三处违反（读的投影 ≠ 写的全量对齐），都有真实数据丢失路径：

1. **`listSites()` 默认 limit 100**（repo 层防慢查询的默认值）被 `buildNavigationData`/`writeNavigationData` 直接使用：
   - 读侧：>100 站点的库，navigation.json 静默截断到 100（首页/后台都少站点）；
   - 写侧：完整快照写回时，超出前 100 的存量站点匹配不到行 → `createSiteWithId` 对**活行** INSERT → 主键冲突 → 整个保存 500。
2. **类目 `enabled` 预过滤**：NavSphere 原版后台（NavigationCard 有「已启用/已禁用」筛选与切换）看不到停用类目；任何一次快照保存把缺席当删除 → 类目被**硬删**（`deleteCategory` 是真 DELETE）、其站点进回收站。渲染层（web `data-loader.filterNavigationData`）本来就过滤三级 enabled，读侧预过滤纯属多余且有害。
3. **不可见记录**：快照线格式只有两级，三级类目（hub 分类页可建，父类目下拉不限制深度）与孤儿 `categoryId` 站点（接口无 FK 强校验，`sites.category_id` 无 REFERENCES）本就不进快照，却被写回顺手清掉。

修法：
- repo 新增 `listAllSites(limit?)`（不分页、快照专用）；storage.ts 读/写两处改用它（上限 `NAVHUB_NAVIGATION_MAX_SITES`）。
- `buildNavigationData` 去掉 enabled 过滤（可见性交给渲染层）。
- `writeNavigationData` 计算「可见集」= 顶级类目 + 直接子类目，删除只对可见集内的记录生效（类目与站点各自判定）。

验证：
- 新测试 `apps/api/test/navigation-snapshot.test.ts`（3 条）**先对旧代码跑过、3 条全红**（实测证据：截断 100/120、停用类目消失、三级类目被删），修复后全绿。
- store 层补 `listAllSites` 单测（105 站点：listSites 截 100、listAllSites 全量、软删不参与）。
- E2E（真实脏库 57 站点 + 真实前端）：停用 `cat-ai`（15 站点）→ navigation.json 仍含该类目 enabled=false（修前会整类目消失）→ 原样 PUT 写回 200 → 类目与 15 个站点全部幸存 → 首页 HTML 里该类目/站点 0 次出现（渲染层过滤生效，对照站点 3 次）→ 重新启用后站点重新渲染。数据可无损往返。
- 全量：tsc 0、vitest 75 文件 1050 通过 15 跳过。
