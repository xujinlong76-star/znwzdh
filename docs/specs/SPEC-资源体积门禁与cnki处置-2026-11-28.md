## 2. 裁决 A —— 门禁挂哪一档：**pre-push 主档（新增 `--unpushed` 模式）+ CI 兜底；pre-commit 不加**

### 2.1 结论

1. **pre-push 新增一枚 `public-asset-size-unpushed`**，调 `node scripts/check-public-asset-size.mjs --unpushed`，登记 `scripts/gates.json` `when: "prepush"`，接线进 `scripts/prepush-gates.mjs` 的 `planGates()` + `RUNNERS`。
2. **CI 登记一枚 `when: "ci"`**，在 `test-web` 作业内、`pnpm --filter navsphere build` **之前**跑全量扫描。
3. **pre-commit 不加**。

### 2.2 理由（按本仓既有取舍逻辑，逐条可复核）

**① 为什么不选 pre-commit（否决 ①）**
- pre-commit 已是 16 枚串行门禁（`gates.json` `when:"staged"` 计数 = 16）。每枚都吃一次进程启动 + 扫描；这枚要扫 388 文件 / 275ms，而它唯独对「本次提交碰了 `brand-icons/`」的少数场景有价值。
- 更关键：**pre-commit 可被 `git commit --no-verify` 绕过**——既有的取舍逻辑明确要求「可被绕过的要往 pre-push 补一道」。既然 pre-push 无论如何都得有，那 pre-commit 这一道就是**纯重复**，不构成纵深。
- 反例校验：`check-large-files.mjs` 同时挂了 staged 与 unpushed。但它的 staged 是**必需**的——50 MiB 大文件一旦提交就只能重写历史，拦在 pre-commit 是唯一止损点。体积门禁不同：260 KB 图标提交了也能一个 revert 修掉，没有「不可逆」这个约束，因此不需要抢在提交前。

**② 为什么是 pre-push 而不是只进 CI（否决 ③）**
- CI 反馈最慢（要等 build + 全量 job），而这类错误的修法极简单（换格式 / 换图）。左移到 push 前，一次 275ms 换掉一轮 CI 往返。
- 本仓已有同类先例：`check-bundle-budget` 的动机就写在 `prepush-gates.mjs:11-14`——「这类问题的 CI 反馈是最慢也最难懂的：tsc/eslint/build 全绿，直到 check-bundle-budget 报『首屏超预算』才知道，且没有线索指向根因」。资源体积门禁是同一族问题。

**③ 为什么 pre-push 必须用 `--unpushed` 而不是全量扫工作区（工单未提，但这是关键）**
`prepush-gates.mjs:38-41` 已经写明这条教训：
> 「这两枚检查的是**工作区**，而推送出去的是**提交**。两者不一致时跑出来的红与本次推送无关，只会冤枉人。」

本仓长期多会话并行。若 pre-push 直接全量扫 `apps/web-overlay/public`，则**别人未提交的 260 KB 图标会挡住我的推送**——这正是 `rest-contracts` / `scope-explicit` 两枚必须带 `dirty` 跳过语义的原因（`prepush-gates.mjs:73-88`）。`check-large-files --unpushed` 已经给出正解：读 `git cat-file` 的**未推送 blob**，别人的工作区改动进不了视野，且能抓住多次提交累积。

### 2.3 接线三向一致（实施方照做，架构师已核过坐标）

| 面 | 文件 | 具体改动 |
|---|---|---|
| 脚本 | `scripts/check-public-asset-size.mjs` | 新增 `--unpushed` 模式：`git rev-list --objects HEAD --not --remotes` 取未推送 blob → `git cat-file --batch-check='%(objectname) %(objectsize) %(rest)'` 取**未压缩大小** → 按同一套 `LIMITS` 判定。缺省（无参数）保持现有全量 walk，供 CI 用。用法串同步写在文件头。 |
| 登记 | `scripts/gates.json` | 追加两条：`{ name:"public-asset-size-unpushed", when:"prepush", script:"scripts/check-public-asset-size.mjs", args:"--unpushed", blocks:true, why:"..." }` 与 `{ name:"public-asset-size", when:"ci", job:"test-web", blocks:true, why:"..." }`。**`test` / `whyNoTest` 必填其一**——建议写 `whyNoTest`，理由：「脚本是对 public/ 目录的薄遍历（阈值表 + statSync），单测只能复述实现；真实回归由 pre-push 与 CI 直接执行本脚本来暴露」，与 `extensions` / `upstream-ref` 两枚的既有写法同款。 |
| pre-push 接线 | `scripts/prepush-gates.mjs` | ① `planGates()` 追加 `{ id:"public-asset-size-unpushed", title:"公共静态资源未超体积上限", run:true, skipReason:"" }`——`run:true` 是刻意的：它读的是提交内容，与 `dirty` 无关，与 `core-mirrors` / `test-mirror-pairs` 同款；② `RUNNERS` 加 `"public-asset-size-unpushed": runPublicAssetSizeGate`；③ `FIX_HINTS` 加一条修复提示（见 §4.4）。 |
| CI 接线 | `.github/workflows/ci.yml` | `test-web` 作业内，`check-no-raw-palette`（`:268`）之后、`pnpm --filter navsphere build`（`:270`）之前插入 `- run: node scripts/check-public-asset-size.mjs` + `id: web-asset-size`。**必须在 build 之前**：它只读 `apps/web-overlay/public` 静态文件，不依赖构建产物，放前面反馈更快。 |

### 2.4 `check-gates-registry.mjs` 为什么能过（推理，未实跑）

该脚本做的是**坐标双向对照**（`scripts/lib/gates-registry.mjs:1-18`）：登记 ↔ 接线，两个方向各查一次。按上表：

- **prepush 方向**：`reviewGates()` 拿 `planGates({}).map(g => g.id)`（`check-gates-registry.mjs:83`）作为「实际接线集合」。上表已把 `public-asset-size-unpushed` 加进 `planGates()` → 登记集 ∩ 接线集 = 该 id，**双向匹配**。
- **ci 方向**：`when:"ci"` 条目按 `job` 名对照 `ci.yml` 的作业与 `ci-passed.needs`。`test-web` 是既有作业名（`gates.json` 里 `test-web` 已登记），**不新增作业、不改 needs** → 不会触发「CI 作业缺登记」。
- **staged 方向**：不新增 staged 条目，且 `install-git-hooks.mjs` 的 pre-commit 模板不动 → 不会出现「登记了没接线」。
- **出口**：`whyNoTest` 已给（不是裸门禁），满足 `validateRegistry` 的形状要求。

**风险点（实施方必须注意）**：`gates.json` 的 `updatedAt` 应从 `"2026-11-21"` 改为 `"2026-11-28"`；某些校验会比对它。

## 3. 裁决 B —— cnki.svg 处置：**位图化为 `cnki.png`（128×30，PNG）**

### 3.1 结论

| 项 | 值 |
|---|---|
| 目标文件 | `apps/web-overlay/public/brand-icons/cnki.png`（删除 `cnki.svg`） |
| 目标尺寸 | **128 × 30**（viewBox 比例 2941.51 : 685.5 = 4.2905，128/4.2905 = 29.8 → 30） |
| 目标格式 | **PNG**（RGBA，保留透明通道） |
| 目标体积 | 实测 **3.53 KB**；设**硬上限 120 KB**（= 现有 `brandIconAnyKb`，不新增阈值） |
| 生成方式 | 一次性脚本（不进仓库运行时），用 `apps/web/node_modules/sharp`（**已验证可加载：sharp 0.35.5**） |

### 3.2 为什么是 b2 而不是 b1 / b3

- **否决 b1（给 brand-icons 加宽版标例外）**：例外一旦开口，「下一个 260 KB 也能援引先例」。阈值表的价值在于**不可协商**；文件本身有更便宜的出路时，绝不开口子。
- **否决 b3（引 svgo）**：本仓 `package.json` 对 `svgo` / `imagemin` / `sharp`（根级）命中 **0**；给一份图标引入构建依赖，收益（最多把 260 KB 压到 120 KB 级，仍超 50 KB）远小于长期的依赖面成本。

### 3.3 可行性判断依据（不是猜的，是量过的）

**① 真实渲染尺寸决定目标分辨率（关键推理）**
`SiteFavicon` 用 `object-contain`，容器是方框；4.29:1 的宽版标在方框里只能按**宽度撑满**，高度 = 宽/4.29。

| 使用点 | 容器 | 有效内容宽 | 实际渲染高 |
|---|---|---|---|
| `navigation-card.tsx:685` 常规卡 | `h-10 w-10` + `p-1.5` | 28px | ~6.5px |
| `navigation-card.tsx:685` 大卡 | `h-13 w-13` + `p-1.5` | 40px | ~9px |
| `site-detail-view.tsx:654` 详情页头图（最大） | `w-16 h-16` + `p-2` | **48px** | ~11px |
| `site-peek-dialog.tsx:304` 速览弹窗 | `w-11 h-11` + `p-2` | 28px | ~6.5px |

**最大值是 48px 宽**（详情页）。128px 位图在 2× DPR 下需要 96px、2.67× DPR 下需要 128px → **128px 覆盖到 2.67× DPR，足够**（本仓既有的全部 PNG 图标就走这个「≥128 缩到 128」口径，见 `site-favicon-iconbatch-c10.test.ts:111-125`）。
若将来详情页图标放大到 `w-20`（80px 内容），届时重出 240px 版本即可——这类资产的换代成本是一次 3 KB 替换。

**② 位图化不会糊（已实测渲染核对）**
我用 `sharp` 以 600 density 光栅化后按真实显示尺寸渲染并放大查看：
- 28px 显示（小卡）：只有零散白块，**不可读**——但那与现在的 SVG 表现**完全一致**（同一几何、同一 sub-pixel 缩放）。
- 112px 显示：`CNKI` / `中国知网` / `www.cnki.net` 三行**清晰可辨**。

⇒ 位图化没有「多丢」任何东西，因为**原 SVG 在真实显示尺寸下本来就丢这些细节**。

**③ 细描边必然丢，且不影响（先承认，不回避）**
SVG 里有 `.cls-3{stroke-width:0.03px}` 与 `.cls-4{stroke-width:0.5px}`（`stroke:#fff`）。在 2941 单位 viewBox、128px 输出下，缩放比 = 128/2941.51 = 0.0435：
- `0.03px` × 0.0435 = **0.0013px**（早已不可见）
- `0.5px` × 0.0435 = **0.022px**（同样不可见）

即使在 48px 真实显示下，这两条线的物理宽度是 0.0005px / 0.008px——**在当前任何设备上都不构成可见笔画**。位图化把它们丢掉，等于丢掉「本来就渲染不出来的东西」。

**④ 白色反白 + 深色底块的机制不受影响**
样式表只有 `#fff`（主体）与 `#f29600`（橙点）。PNG 保留 RGBA（实测 `hasAlpha: true`、`channels: 4`、alpha min/max = 0/255 → 真实透明），所以 `LOGO_TILE_MAP['cnki.net'] = 'dark'` 的深色底块照常生效，**白色主体在深色底上依然可见**。
