> 检测时间：2026-10-26 ｜ 检测方式：Playwright + 本机系统 Chrome（headless）真实点击 / 输入 / 滚动 / 跳转

## 一、概述与方法论

本次检测用**真实浏览器**（非纯接口探测）模拟真人操作，遍历全站已知路由并辅以受控链接发现，覆盖全部主用户路径：搜索、分类浏览、站点详情、分页、偏好设置、投稿表单、插件市场安装、自定义工作台编辑/拖拽、鉴权重定向、弹窗、移动端适配。

- **控制台 / 网络捕获**：监听 `console(error)`、`pageerror`、`requestfailed`、`response(4xx/5xx)`、水平溢出（`scrollWidth > innerWidth + 2`）、空数据标记。
- **三个自动化脚本**：`crawl.mjs`（140 页全量爬取，记录 4xx 的**来源页**）、`interactions.mjs`（14 项核心交互）、`mobile.mjs`（20 页移动端 390×844）；三者均支持 `NAVHUB_AUDIT_BASE` 指向任意环境。
- **专项探针**：`verify-progressive-disclosure.mjs`（首页渐进披露：截断生效 / 展开收起可逆 / 零请求 / 移动端不溢出）、`trace-4xx-origin.mjs`（4xx → 来源页归因）、`scan-suspicious-links.mjs`（全站 HTML 坏链扫描）。
- **修复后回归**：对受影响路由做针对性复测，并全量重跑爬取确认无回退。
- **生产构建复核**：以 `NEXT_DIST_DIR=.next-prod-audit3 next build` + `next start -p 3212` 出**生产产物**重跑整套（buildId 已在 HTML 中核验），用于排除 dev 模式的编译/阻塞假象（dev 下曾出现 `goto(load)` 超时与服务重启）。

## 三、问题清单与修复结果（按优先级）

### 🔴 P1 — `/graph` 页面 React 水合（hydration）不匹配

- **页面/模块**：`/graph`（组件 `EcosystemGraph`）
- **复现步骤**：浏览器打开 `/graph`，查看控制台。
- **严重程度**：中（控制台红色告警；功能不受影响，但属 React 官方不推荐的非确定性 SSR 渲染）
- **可能原因**：SVG 节点坐标由浮点运算（`Math.cos/sin`）算出，服务端序列化尾差与客户端计算值在第 15–17 位有效数字出现分歧（如 `y2="67.24043469662439"` vs `67.24043469662445`），触发 React 水合告警。
- **修复**：
  - 文件：`apps/web-overlay/src/components/ecosystem-graph.tsx`（已同步至 `apps/web`）
  - 关键改动：新增 `graphMounted` 状态 + `useEffect` 置位；**坐标相关的 `<svg>` 推迟到客户端挂载后再渲染**，首屏仅服务端渲染外壳与说明文案（SEO 内容不损失）。消除 SSR/CSR 坐标分歧。
- **修复后验证**：`/graph` 控制台 `consoleErrors=[]`、`pageErrors=[]`；挂载后 SVG 正常渲染（实测 71 个节点圆），功能完整。

### 🔴 P1/P2 — 匿名访问时稳定产生 401 控制台噪声

- **页面/模块**：`/preferences`、`/me`、`/favorites`、`/me/workspaces`
- **复现步骤**：未登录打开上述任一页面，观察控制台。
- **严重程度**：中（每条 401 都会让浏览器在控制台刷 `Failed to load resource: 401`，淹没真实错误）
- **可能原因**：这些页面的用量卡 / 成员列表**无论是否登录都发起鉴权接口请求**，匿名访客必然 401。
- **修复（分两处）**：
  1. 文件：`apps/web-overlay/src/components/ai/llm-usage-card.tsx`
     - 关键改动：改用**命令式 `getSession()`**（不依赖 `<SessionProvider>` 上下文，避免在某些渲染子树缺失 Provider 时 `useSession` 直接抛错导致整卡崩溃）判定登录态，**仅在确认已登录后才请求 `/api/me/llm-usage`**，从源头消除匿名 401。
  2. 文件：`apps/web-overlay/src/app/me/workspaces/page.tsx`
     - 关键改动：复用既有 `useIdentityReady().isAnonymous` 信号，**匿名态跳过 `fetchWorkspaceMembers`**（成员列表是登录账号私有数据；匿名态界面已给出「登录后邀请协作者」入口），避免 `/api/hub/workspaces/ws-personal/members` 的 401 与误导性的「暂时取不到」错误提示。
- **修复后验证**：`/preferences`、`/me`、`/favorites`、`/me/workspaces` 的 `badResponses=[]`、`consoleErrors=[]`。

### 🟠 P2 — `/me/notifications` 匿名访问仍发起受保护请求（401 噪声收尾）

- **页面/模块**：`/me/notifications`（通知面板）
- **复现步骤**：未登录打开 `/me/notifications`，控制台出现 2 条 `401 /api/me/notifications?limit=20&offset=0`（StrictMode 双调用）。
- **严重程度**：低-中（页面已有 401 兜底会渲染空态，但请求本身仍会产生控制台红字）
- **可能原因**：页面挂载即无条件 `fetch('/api/me/notifications')`，未先判定登录态。
- **修复**：
  - 文件：`apps/web-overlay/src/app/me/notifications/page.tsx`（已同步至 `apps/web`）
  - 关键改动：引入 `useIdentityReady()`，**`ready` 前不发请求**；`isAnonymous` 时直接渲染空态并**完全不发起请求**；仅确认已登录才 `load(0)`。setState 仍放微任务，遵守 `set-state-in-effect` 约定。
- **修复后验证**：`/me/notifications` 的 `meNotificationsRequests=0`、`badNew=[]`、空态文案正常显示（`emptyStateShown=true`）。

### 🟠 P2 — 搜索引擎包详情页把 emoji 当 `<img src>`，每页 6 条 404

- **页面/模块**：`/marketplace/code-and-package-search-pack`、`/marketplace/ai-deep-search-pack`（所有 `search-pack` 详情页的「包含的快捷搜索引擎」区块）
- **复现步骤**：打开任一搜索引擎包详情页 → Network 出现 `/marketplace/%F0%9F%94%8E`、`/marketplace/%E2%9A%A1` 等 **404**（每页 6 条）。
- **严重程度**：中（每次访问必现；污染 Network/控制台，图标显示为破图，且搜索引擎图标完全丢失）
- **可能原因**：`detail-tab-panels.tsx` 直接写 `src={eng.icon}`。而清单契约里搜索引擎的 `icon` 是 **emoji 短文本**（种子数据为 `"⚡"`/`"🔎"`/`"✨"` 等），浏览器把 `src="🔎"` 按**当前路径**解析成相对地址 → `/marketplace/%F0%9F%94%8E`。
- **修复**：
  - 文件：`apps/web-overlay/src/app/marketplace/[slug]/detail-tab-panels.tsx`（已同步至 `apps/web`）
  - 关键改动：新增 `isImageIcon()`（仅 `http(s)://`、站内 `/`、`data:image/`、`blob:` 走 `<img>`），其余按 **emoji 文本**渲染为 `<span aria-hidden>`。图标在两种形态下都能正确显示，且不再产生请求。
- **修复后验证**：两个搜索包页 **4xx = none**（修复前各 6 条）。

### 🟠 P2 — `broken` 站点的标签链指向 404 标签页

- **页面/模块**：`/site/[id]`（话题标签 chips）
- **复现步骤**：打开 `/site/0248542c-f839-4527-aee9-a89280ef9e32`（CodePen）或 `/site/0269d801-195e-4d59-a533-aad0b280cd33`（Grok），点击 `#codepen` / `#xai` / `#实时信息` → `/tags/...` **404**。
- **严重程度**：中（内链把用户送进 404；对 SEO 也是坏内链）
- **可能原因**：这两个站点 `status = "broken"`。标签页只统计 `active` 站点（`listTagsWithCounts` 的 JOIN 条件刻意如此），0 存活站点 → `notFound()` 真 404；但站点详情页对 broken 站仍可访问，且**无条件把标签渲染成链接**。经验证：**唯一会产生 404 标签链的就是非 active 站点**（active 站点的标签计数 ≥1，标签页必然存在）。
- **修复**：
  - 文件：`apps/web-overlay/src/components/site-detail-view.tsx`（已同步至 `apps/web`）
  - 关键改动：`site.status !== 'active'` 时把标签降级为**纯文本 chip**（样式不变、不再可点），active 站点保持内链（保留权重传递）。
- **修复后验证**：两个站点页 **4xx = none**，标签渲染为 `#codepen`/`#演示`、`#实时信息`/`#xai` 文本 chip，`a[href^="/tags/"]` 数量为 0。

### 🟠 P2 — 首页 HTML 超出体积预算 68%（6901 KB / 4096 KB），改为渐进披露

- **页面/模块**：首页 `/`（`NavigationContent` → `NavigationCategorySection` → `NavigationCard`）
- **复现步骤**：`node scripts/html-budget.mjs --url=http://<host>/` → `{"kb":6901.4,"budgetKb":4096,"ok":false}`。
- **严重程度**：中（不影响首屏可用性，但解析/水合成本随卡数线性增长；项目自带哨兵已在报错，且是唯一能让首页随时间持续膨胀的入口）
- **可能原因**：首页把**全部站点卡片一次性 SSR**：1008 张卡 × 约 6.2 KB = 6084 KB，固定开销仅 772 KB。单卡 6.2 KB 的构成是 **class 属性约 3.0 KB（49%）+ 内联 `<svg>` 约 1.9 KB（28%）**——Tailwind 类名与内联图标无法靠「精简卡片」压下去，只能减少首屏卡数。
- **量化对比（先证明「压单卡」不可行）**：
  - 仅做图标 sprite 化最多省约 1.5 MB → 仍有 5.4 MB，超预算；
  - 按叶子列表限 8 张 → 4363 KB（仍超）；限 10 → 5093 KB；限 12 → 5500 KB。**要压到 4096 KB 以下，必须每组 ≤6 张**。
- **修复**（决策：**不牺牲信息架构，改用渐进披露**）：
  - 文件：`apps/web-overlay/src/components/navigation-category-section.tsx`、`navigation-content.tsx`、`app/page.tsx`（均已同步至 `apps/web`）
  - 关键改动：
    1. 每组（分类直属站点 + 每个二级分类）首屏只渲染前 **6** 张，超出部分显示「展开全部 N 个」按钮；点击后**客户端即时**揭示，**零请求、无加载态**（数据本就在 props 里，RSC 序列化仅 0.42 MB，成本全在 DOM）。
    2. 开关状态 `expandedGroups` 初始为收起，服务端与客户端一致 → **不产生水合分叉**；`aria-expanded` 同步、`col-span-full` 占满整行不留空、`data-group-toggle` 作为稳定测试钩子。
    3. **排版编辑 / 多选模式下自动全量展示**（那时用户要对全部卡片动手，折叠会让卡片「消失」）。
    4. 上限由服务端 `NAVHUB_HOME_CARDS_PER_GROUP` 注入（`app/page.tsx` 读取），传 `0` 即恢复全量 SSR 旧行为；非法值退回默认，不让错字把首页变空。
- **修复后验证**（真实浏览器 + 官方哨兵）：
  - 哨兵：**`{"kb":3600,"budgetKb":4096,"ok":true}`**（6901.4 → 3600 KB，**−48%**；卡片 1008 → **443**，`展开全部` 按钮 69 个）。
  - `verify-progressive-disclosure.mjs`：组内 **6 → 16**、全页 **443 → 453**、按钮文案 `展开全部 16 个 → 收起`、再点回到 **6 / 443**；**展开与收起全程 `fetch/xhr` = 0**；390px 展开态**无水平溢出**；控制台错误 / 页面错误 / 4xx 全为 0。
  - 交互套件仍 **14/14**，140 页仍全 200（见 4.7）。

### 🟡 观察项（性能 / 一致性）

- **✅ 首页 HTML 预算（已修复，见上文 P2）**：哨兵现为 `{"kb":3600,"budgetKb":4096,"ok":true}`。两点补充事实：
  - **该哨兵已接入 CI（2026-10-26 补做）**：`.github/workflows/ci.yml` 的 `seo-audit-prod` 作业新增「首页 HTML 预算（解压后，真实数据）」步骤，`--max-kb=4096` 显式写在 CI 里。**刻意不挂 PR 门禁**：PR 的种子库只有几十个站点，量出来必然远低于阈值，那只会制造「已覆盖」的错觉；`seo-audit-prod` 是唯一带真实站点库的运行环境（`workflow_dispatch` 手动触发）。
  - 传输侧一直是健康的：gzip 后约 350 KB、生产暖机 TTFB 0.13–0.19 s。优化目标是**解压后 DOM 的解析与水合**，不是带宽。
- **`/me`、`/favorites` 不强制跳登录**（与 `/admin` 307 跳登录不一致）：**决定维持现状**。收藏/账号是「匿名也能看空态」的个人页，`/admin` 是管理后台，两者性质不同；统一重定向会制造无谓跳转，也会挡住首次访问的空态引导。
- **多选「全选」的计数口径**：多选模式会**自动展开全部卡片**（避免用户找不到被折叠的卡），而工具栏「全选可见站点」统计的是**当前视图内的全部站点**（含未展开的）。计数本身会如实显示（例如 1008），但「可见」二字在渐进披露后略不精确——**行为是对的（批量操作本就该覆盖全部分类下站点），只是措辞可再打磨**，本次不改文案以免牵动 a11y 测试。
