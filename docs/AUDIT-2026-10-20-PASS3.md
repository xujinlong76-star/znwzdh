## 2. 安全

### 2.1【P1·已修复】身份签名可被请求体完全绕过

**位置**：`apps/api/src/server.ts`（原 310–329 行）→ 现 `preValidation` 钩子

**问题**：`NAVHUB_IDENTITY_SECRET` 的设计目标是「任何人都不能自称他人 userId/anonId」。但校验挂在 `onRequest`——Fastify 生命周期的第一站，**此时 body 尚未解析**。而路由侧读取身份的 `identityOf()` 顺序是 Header → Query → **Body**。

于是：

```
POST /api/favorites
{ "userId": "github:victim", "siteId": "..." }     ← 不带任何签名
```

在 `onRequest` 里 `identityOf()` 拿到 `null` → 整段校验被跳过 → 路由随后从 body 读出 `github:victim` 并照常执行。**配了密钥也等于没配**，且完全无日志。

**修复**：校验整体迁移到 `preValidation`（body 解析完成、业务处理之前），Header/Query/Body 三个入口一并覆盖。

**非空性验证**：把钩子临时改回 `onRequest` 后，新增的 3 条测试中 2 条立即失败（`404` 而非预期的 `401`）；恢复后 12/12 通过。

**影响面**：仅影响「配置了 `NAVHUB_IDENTITY_SECRET`」的部署；未配置时行为与历史版本逐字节一致（零回归）。

## 3. 正确性

### 3.1【P1·已修复】迁移层 9 处方言判断永远不成立

**位置**：`packages/store/src/migrate.ts`

**问题**：`Db.dialect` 的取值是 `"sqlite" | "pg" | "libsql"`，但迁移层 9 处写的是 `db.dialect === "postgres"`。全仓库其余 20+ 处（`repository/*`、`search.ts`、`jobs.ts`）用的都是 `"pg"`——只有这里写错。

后果：PostgreSQL 部署在「补表」路径上拿到的是 **SQLite 版 DDL**：

- `created_at INTEGER`（2038 溢出）、`confidence REAL`（4 字节精度）
- `is_free_or_open_source INTEGER DEFAULT 0` 冒充 `BOOLEAN`

之所以一直没炸：`driver.ts` 的 `DDL_PG` 先建过这些表，`CREATE TABLE IF NOT EXISTS` 变成空操作。**任何「只在 migrate 里新增、忘了同步 DDL_PG」的表都会立刻踩中**——这是一颗定时炸弹，不是理论问题。

顺带修掉同类缺陷：分派写成 `dialect === "sqlite" ? sqlite.exec : pg.query`，libsql 会走进 `pg` 分支（不存在）→ 抛错 → 被 `catch` 静默吞掉，**libsql 的迁移一条都没执行过**。现改为「非 pg 走同步 runner」，并对 libsql 的异步返回做归一化。

**回归测试**：`packages/store/test/migrate-dialect.test.ts`（5 条）用假 DB 记录下发语句，断言 PG 分支必须出现 `BOOLEAN` / `BIGINT` / `DOUBLE PRECISION`，libsql 必须走 `exec`。

### 3.2【P1·已修复】libsql 方言「静默返回空结果」

**位置**：`packages/store/src/driver.ts`

**问题**：`Db.sqlite` 是**同步**接口（better-sqlite3 语义），调用方写完 `.all()` 就当数组用；而 `@libsql/client` 的 `execute()` 返回 Promise。旧适配层把 Promise 原样当作 `{ rows }` 返回，于是**每一次查询在上层都表现为空数组**：不抛错、不打日志，列表永远空、计数永远 0。

**修复**：该方言在 README / 配置项中均未宣传，属于未完成的死代码。直接 fail fast，抛出具名错误说明「同步接口与异步驱动不兼容，请用 sqlite 或 pg」。宁可启动失败，也不要让部署在「没有任何数据」的假象里跑下去。

**回归测试**：`driver-pragma.test.ts` 新增 1 条，断言 `openDb({dialect:"libsql"})` 抛错且消息可操作。

### 3.3【P1·已修复】AI 审查把「网络抖动」判成「死链」，误驳回合规插件

**位置**：`apps/api/src/ai-plugin-auditor.ts`

**问题**：外链探活只有「ok / 失败」两态，超时、连接重置、403 反爬、429 限流、502 源站抖动**全部算失败**。存活率进入 25% 权重的可用性分，并在 <50% 时再扣合规 20 分、相关性 15 分——一个完全正常的插件会因审核机网络打嗝被自动驳回，作者只看到「存活率 43%」，无从申辩。

这不是理论风险：全量测试下该用例**稳定复现**（我在第一次 `verify` 里就撞到 `expected 'rejected' to be 'published'`），单独跑则通过——正是「负载高 → 探针超时 → 误判」的典型特征。

**修复**：

1. **三分类**：`ok` / `dead` / `inconclusive`。只有非法 URL、404、410、451 计入「确认失效」；超时、DNS 抖动、401/403/429/5xx 一律「不可判定」，**从分母中剔除**（与仓库链接体检脚本的口径一致）。
2. **并发上限 6**（原来最多 30 个并发直扑外站）：既对目标站点礼貌，也避免把本机连接池打满自造超时。

**回归测试**：`ai-plugin-probe-classify.test.ts`（4 条）锁定分类矩阵；全量套件下该用例从「必现失败」变为稳定通过。

### 3.4【P2·仅报告】事务与异步交错的结构性风险

`Repository.withTransaction` 用 `BEGIN IMMEDIATE` + `txLock` 串行化，但事务体内部存在 `await`（如 `mergeCategories` 逐个站点 `UPDATE`）。Node 单线程在 `await` 处会让出事件循环，**并发的非事务查询可能落进这个已打开的事务**，一旦回滚就连带丢失。

- 触发条件：并发写 + 事务体含 `await`（当前有 15 处 `withTransaction` 调用）。
- 建议：事务体内只做同步 DB 调用（把 `await repo.listSites` 换成一次性 SQL），或引入全局写锁。
- 未改动原因：涉及 15 个调用点的语义调整，超出「最小改动」边界，且并行会话正在改相关仓储。

## 4. 性能

### 4.1【P0·已优化】插件市场列表单次响应 1.16MB

**位置**：`apps/api/src/routes/plugins.ts`（`GET /api/plugins`）

**定位过程**：接口基准里唯一异常项——`/api/plugins` p50 87ms，其余接口 6–23ms。进一步测量发现响应体 **1,157,817 字节**，其中 **729,947 字节（63%）是 site-pack 的完整 manifest**（单个约 34KB，含最多 200 站点 + 20 分类）。

**关键判断**：列表页的任何消费者都不读 site-pack 的 manifest——

- 卡片只用 `summary`（`siteCount` / `categoryCount` / `hosts`）；
- 详情页与安装弹窗走 `GET /api/plugins/:slug`；
- 安装动作由服务端按 slug 读库，不需要浏览器上传清单。

真正需要清单的只有「复制 JSON 清单」这类工具场景（Raycast 扩展）。

**修复**：默认对 `site-pack` 剥离 `manifest`（保留 `summary`），新增 `?manifest=1` 显式取全量；Raycast 扩展同步改为带该参数，功能不受影响。

**实测（同一份 1020 站点 / 64 插件的数据快照）**

| 场景 | 响应体 | 服务端耗时 |
|---|---|---|
| 修复前 | 1,157,817 B | 75.9 ms |
| 修复后（默认） | **36,820 B** | **51.2 ms** |
| 修复后 + gzip | **10,230 B** | 52 ms |
| `?manifest=1`（工具场景） | 1,157,817 B | 75.9 ms |

**回归测试**：`apps/api/test/plugin-list-payload.test.ts`（3 条）锁定「site-pack 默认无 manifest / theme 保留 / `manifest=1` 全量」。

### 4.2【P1·已优化】全站零 HTTP 压缩

**位置**：新增 `apps/api/src/http-compression.ts`，在 `main.ts` 的 `listen()` 之前注册。

**问题**：默认部署（docker-compose 双服务、无反向代理）**没有任何压缩**。1.16MB 的 JSON 原样走网络，弱网下就是数秒白屏。

**实现要点**（都在测试里钉住）：

- 只压 JSON / 文本 / SVG，**显式排除 `text/event-stream`**（压缩窗口会缓冲 SSE 事件，实时性直接没了）；
- 已带 `content-encoding` 的不二次压缩；
- 只处理 string/Buffer，流式响应直接放行；
- `Vary` 用**累加**而非覆盖（CORS 已写 `Vary: Origin`，覆盖会让共享缓存串源）；
- 移除旧的 `content-length`，由 Fastify 按新 payload 重算；
- `gzip;q=0` 视为拒绝（RFC 9110）。

**实测**：`/api/docs` 140,265 B → 4,350 B（32×）；插件列表 36,820 B → 10,230 B（3.6×）。

**为什么不引 `@fastify/compress`**：需求只有「>1KB 的文本响应 gzip」，30 行钩子可覆盖；项目一贯保持核心零额外依赖（安全头、指标、限流均为手写或官方插件）。

### 4.3【P2·已优化】管理台 SSE 心跳 6 条 COUNT → 1 条

**位置**：`packages/store/src/repository/stats.ts`

`stats()` 被 `/api/stats`、管理台总览、以及**每 3 秒一次**的 SSE 心跳调用。旧实现串行发 6 条 `COUNT`，一个管理台页面开一天 ≈ 17 万次查询。合并为单条 SQL（6 个标量子查询），一次往返完成；PG 的 bigint 字符串统一 `Number()` 收敛。

### 4.4 复测确认无回归的路径

|---|---|---|

### 6.1【阻塞门禁】并行会话的 3 处 overlay 漂移

`check-web-overlay` 报 3 个文件内容漂移（overlay 与 vendored `apps/web` 不一致）：

- `src/components/ai/ai-copilot-drawer.tsx`

修复命令：`node scripts/check-web-overlay.mjs --fix`。**我没有执行**——这三个文件在审查期间仍被并行会话写入，此时同步可能把半成品镜像进 vendored 目录。建议该会话收尾后统一同步。

### 6.2【P2】前端读请求没有超时

`apps/web-overlay/src/lib/navhub-api.ts` 的 `getJson()` 无 `AbortSignal` 兜底。中枢「TCP 连上但不回包」时，按钮会永远转圈，用户既看不到错误也拿不到重试入口（代理侧默认 30s 超时兜底，但直连场景没有）。建议：`signal ?? AbortSignal.timeout(30_000)`，AI 生成类 POST 保持现状。

### 6.3【P3】收藏按钮快速双击会插入重复项

`useFavorites.toggle()` 基于闭包里的 `items` 计算 `next`，两次点击同一渲染帧会各自得到「未收藏」的结论并各插一条。建议改用函数式更新或 `itemsRef` 镜像。

### 6.4【P3】插件列表服务端仍有 ~50ms

剥离 manifest 后响应只剩 36KB，但 `listPlugins` 仍是 `SELECT p.*`（把 1MB 清单全读出来）+ 对每行 `JSON.parse` + `summarizePluginManifest` 逐站 `new URL()`。若要继续优化，应把 `siteCount/categoryCount/topHosts` 在写入时物化成列（scheme 变更，需迁移）。当前 51ms 在可接受范围，未动。

### 6.5【可选】测试套件可再快 ~60s

vitest 提示：184 个 worker 每个约 1s 启动，`isolate: false` 可省 62s。但本仓库有大量「单例状态 / 计数累加」测试（指标、限流、LRU），关闭隔离可能引入跨文件污染，需逐文件验证后再开——不建议在没有充分时间预算时改。

### 9.1 身份：签名校验的身份 ≠ 实际使用的身份【P0·已修复】

`apps/api/src/routes/plugin-presentation.ts` 的 `extractPluginIdentity` 自己解析身份：**先 body 再 query、截 120 字符**；而签名 hook 用的是 `identityOf`：**Header → Query → Body、截 64**。两边口径不同，于是

- 攻击者在头里签**自己**的身份（签名合法），body 里塞**受害者**的身份（业务照用）→ 以受害者身份安装/卸载、写评价、`GET /api/plugins/mine` 读出对方全部私有草稿；
- 截断长度差还允许「共享 64 字符前缀的更长身份」借用签名。

修复：`extractPluginIdentity` 直接 `return identityOf(req as never)`，让「校验谁」和「当成谁」是同一函数。回归：`apps/api/test/identity-plugin-impersonation.test.ts`（4 例：头签自己+body 塞别人 / POST body 同招 / 长身份借用 / 合法自查仍通）。回退验证：还原旧解析后**四例全红**——连「只在 Header 里带身份」的合法自查也 400，因为旧实现根本不看 Header。

### 9.2 HTTP 语义：缓存、HEAD、代理信任【P1·已修复】

| 位置 | 症状 | 根因（实测） | 处置 |
|---|---|---|---|
| `routes/plugins.ts` 徽章 | README/官网上的徽章每次加载都回源，偶发 429 碎图 | 路由里手写的 `cache-control: public, max-age=300` 被 `server.ts` 的 onSend 钩子整行覆盖成 `no-store`（未声明 `config.cache` 的 GET 一律 no-store）；回源又去抢全局 300/min/IP 的限流桶 | 改为 `config.cache = { maxAge: 300, etag: true }`；5 分钟浏览器缓存 + 过期后走 304，不再重复渲染 SVG、不再占限流额度 |
| `server.ts` onSend | 所有 HEAD 恒 `no-store` 且无 ETag | 条件写的是 `method !== "GET"`，而 `exposeHeadRoutes` 会按 GET 自动生成 HEAD。实测 onSend 里 HEAD 的 payload 仍是**完整表示**（Fastify 只在写 socket 时剥 body，`content-length` 保留），所以 GET 的缓存/ETag 逻辑对 HEAD 同样安全 | 放行 GET 与 HEAD 同一策略；断言两者头字段完全一致 |

回归：`apps/api/test/response-cache-headers.test.ts`（9 例：徽章 200/304/404、HEAD 与 GET 头一致、HEAD 条件请求、POST 仍 no-store、rank 两端点缓存与 404）、`apps/api/test/trust-proxy-mode.test.ts`（8 例：解析矩阵 + 起真实服务断言 `req.ip` 落到哪一跳）。

拓扑限制（仅报告）：api+web 两容器时，Next.js 的反向代理不会在 XFF 里追加自己的地址，因此 `req.socket.remoteAddress` 就是 web 容器，网段列表只能写到「信任 web 容器」这一层——再往左依然是客户端自报。要真正防伪造，入口得换成能追加 `X-Forwarded-For` 的反代（nginx/traefik）并只信任它。

### 9.5 调度层：单实例锁与 cron 声明【P1·已修复】

**长任务期间锁被合法抢走。** SQLite 的 runner 锁是「锁行 + `created_at`，超 `LOCK_TTL_MS`(120s) 即可被别的实例 UPDATE 夺走」。原先只在**任务之间**续期——而单个任务自己就能跑过 120s：`health_check` 默认巡检 100 个站点是串行抓取（`NAVHUB_FETCH_TIMEOUT_MS` 默认 10s，最坏 100×10s=1000s），`reindex`/`data_retention` 声明的预算就是 600s。TTL 一过，第二个实例按 SQL 语义是完全合法地接管，于是两边同时跑同一批任务：重复抓取、重复写 health/rank、对外站翻倍施压，且谁都不觉得自己重复。

修复：`tick()` 期间以 `LOCK_TTL/3`（40s）心跳续期，退出时 `clearInterval`；新增 `lockHeartbeatMs` 只给测试用。续期语句带 `response = holder` 条件，锁真被夺走时 0 行命中、不顶掉新持有者。回归：`jobs-lock-heartbeat.test.ts`（2 例：任务进行中 `created_at` 被周期性刷新；被接管后旧心跳不覆盖新持有者）。去掉心跳后第 1 例必红（`expected 1792594228732 to be greater than 1792594228732`）。

**cron 别名表缺 `DAILY4AM`。** `scheduleCronOf("data_retention")` 走 `CRON_EXPRS[alias] ?? alias` 的兜底，原样吐出 `"DAILY4AM"`（1 段），`cronDue` 对非 5 段恒判 false——按 cron 排期的话这条任务永远不会触发。今天没炸是因为实际到期判定走 `DEFAULT_CRON_SCHEDULES` 的 `intervalMs`，`cronDue` 只被管理端展示和测试用。补上别名，并把守卫从「手写 7 个 kind 名单」（正好漏掉 data_retention / taxonomy_audit / plugin_governance，所以一直没发现）改成遍历 `DEFAULT_SCHEDULES` 全部 10 个 key，失败信息点名是哪个别名没登记。

**声明值与实现不一致（注释纠偏，不改行为）。** `JobSchedulePolicy.timeoutMs` 原文写着「超时抛错走正常重试链」、`maxConcurrency` 写着「允许的最大并发数」，但两者在生产代码里**从未被读**（`DEFAULT_SCHEDULES` 只用到 `cron`，且没有任何 DB schedule）。为什么不当场实现：handler 里没有 AbortSignal，`Promise.race` 掐不掉正在跑的抓取循环，只会让 Runner 提前把任务标失败并放行下一轮，僵尸 handler 继续跑 → 同一个 kind 被并发执行，比重置为 retrying 更糟；而且这些预算值从未被真实负载验证过（`health_check` 声明 240s，实际最坏 1000s，硬套会让默认巡检天天超时重试）。现在注释明确写出「声明值 / 实际由每次网络调用各自超时兜底 / 要变硬预算需要先把 signal 贯穿 runXxx 与 @navhub/ai」。

## 10. 2026-10-22 凌晨第五轮：部署配置可达性、身份可见性与分面查询放大

前四轮找的是「代码写错了」。本轮问的是两个更容易漏的问题：**已经实现的安全规则在真实部署形态下够不够得到配置**，以及**客户端能控制的读路径参数有没有上限**。两处答案都是「不够」：一组安全变量在 compose 里根本没有入口（其中一条 fail-closed 规则因此是死的），`facets` 在两个入口上既无预算、解析失败还会**静默返回未过滤的全量**。

### 10.1 部署配置：安全变量「文档里有，容器里传不进去」【P1·已修复】

`assertIdentitySecurity`（生产 + `authRequired` ⇒ 必须有 ≥32 字符的身份签名密钥）和「生产 + `publicUrl` 指向公网 + 未开鉴权 ⇒ 拒绝启动」都写进了代码，但 compose 没有给它们配置入口——规则越严格，越会变成一条走不通的死路：

| 变量 | 本轮之前 | 后果 |
|---|---|---|
| `NAVHUB_BOOTSTRAP_TOKEN` | 在 api 服务里是**一整行注释** | 开鉴权后容器内没有首个凭据入口，只能 `docker exec` 进去改环境 |
| `NAVHUB_PUBLIC_URL` | 完全没透传 | config 默认 `http://localhost:8787` ⇒ 判定为内网 ⇒「公网 + 未鉴权就拒绝启动」这条 fail-closed **永不触发** |
| `NAVHUB_IDENTITY_SECRET` | api 与 web **两侧都没有** | ①`AUTH_REQUIRED=1` 时容器里 `NODE_ENV=production`，身份密钥既拿不到也生成不了 ⇒ **无法靠配置自救的崩溃重启循环**（唯一出路是编辑 compose 本身）；②即使在宿主机 export 了，两侧也收不到，签名链路整条失效 |
| `NAVHUB_SESSION_SECRET_PREV` | 没透传 | 密钥轮换的宽限期做不了：新签发立刻生效、旧签名立刻失效 |
| `NAVHUB_ALERT_WEBHOOK` | 没透传 | 任务重试耗尽的告警只能进 console |
| `api-standard` 服务 | **没有任何鉴权相关变量**（连 `NAVHUB_AUTH_REQUIRED` 都没有） | 该 profile 无论怎么设环境都是永久开放模式 |

处置：全部改成活跃的 `KEY: ${VAR:-}` 透传并写清语义。**这是零行为变化的加性改动**——`config.ts` 的 `env()` 把空字符串当作未设置（走 fallback），`bootstrapToken / identitySecret / alertWebhook / previousSecret` 又都 `|| null`，所以 `${VAR:-}` 与「不写这一行」在运行时等价；差别只在于运维**能不能**把它配上。

刻意**没有**像 `SESSION_SECRET` 那样让 entrypoint 自动生成身份密钥：自动生成等于默认开启签名校验，而只有 Web 的 `/api/hub/*` 代理会自动签名——直连中枢的消费者（浏览器扩展、MCP、自建脚本）带的 `anonId/userId` 会立刻全量 401。保持「空 = 不校验」的历史行为，由运维显式开启，但把这个选择摆到台面上（见 10.2）。

回归：`apps/api/test/compose-env-parity.test.ts`（4 例）。用自写的行扫描解析 `environment:` 块（本仓库不引 YAML 依赖），**并且把被注释掉的键也识别出来**——「注释掉」正是本轮要抓的那种错法。断言：①每个中枢/web 服务都**活跃**透传安全变量；②身份密钥同时给到中枢与 Web（只配一侧 = 站点里所有带身份请求 401）；③凭据类变量（`SECRET|TOKEN|PASSWORD|API_KEY`）不得内置默认值，`${X:-硬编码}` 这种会被抓（对应升级方案 P0-1）；④compose 活跃透传的安全变量必须在 `.env.example` 有文档。

### 10.2 身份签名默认关闭，且关闭状态不发出任何提示【P1·已修复（可见性）】

`identitySecret` 为 null 时，`preValidation` 签名钩子第一行就 return；`identityOf` 只是按 Header → Query → Body 取一个 ≤64 字符的字符串。也就是说**默认配置下任何请求都能自称任意身份**，而「按身份隔离」的数据正好包括：`GET/DELETE /api/profile`、`/api/favorites*`、`/api/search-history`、`POST /api/me/merge`、`/api/vault/sync`、`/api/crdt/sync`、`POST /api/users/sync`、`POST /api/plugins*`（含 `/:slug/versions`、`/:slug/reviews`）、`GET /api/plugins/mine`——约 110 条公共路由的隔离强度实际等于一个可自报的字符串。

本轮做的是**可见性**：启动横幅原先会打印「鉴权 未启用」，却对身份签名只字不提。现在两种状态各给一条明确文案，关闭时直接写明「任何请求可自称任意身份」。为什么不顺手把路由收紧：一次性让 110 条路由要求签名，会把所有不签名的直连客户端当场打死；而分批收紧需要先决定「哪些端点算私有数据」，这是产品口径，不是审查能替用户拍的（列为 10.7.1）。

### 10.3 Raycast 扩展：全体用户共用同一个匿名身份【P2·已修复】

`browse-plugins.tsx` 的安装请求硬编码 `?anonId=raycast-user`。两个后果叠在一起：安装量把所有安装者合并成一个人计数；`GET /api/plugins/mine` 会把**别人**装的包显示成自己装的。改为首次运行生成随机 ID 持久化到 Raycast 本地存储（per-install），并从 query 挪到 `x-navhub-anon-id` 头——身份串留在 URL 里会进中枢访问日志、反代日志和浏览器历史。长度主动卡在 64 以内，与 `identityOf` 的截断口径一致，否则「签名的对象」和「实际使用的身份」会因截断分叉（正是 §9.1 那类 bug 的成因）。

### 10.4 公共读路径：`facets` 的参数放大与静默降级【P1·已修复】

| # | 位置 | 症状 | 根因 |
|---|---|---|---|
| A | `routes/sites.ts` | `?facets=<坏 JSON>` 返回 **200 + 未过滤全量** | `try { JSON.parse } catch { /* ignore */ }` 把过滤条件静默丢掉：调用方以为过滤生效，拿到的却是整站列表 |
| B | `routes/search.ts` | `facets` 里嵌对象/`null` 时条件变形，超预算输入直接 500 | zod 用 union + transform，值最终 `String(v)`：`null`→`"null"`、`{}`→`"[object Object]"`；实测未经校验的非法 facets 落到存储层回的是 **500**（既不是 400 也不是静默降级） |
| C | 两个入口 | 单个请求能拼出任意大的语句 | `facets` 的**键数和每键值数都由客户端决定**，值直接进 `IN (...)`，没有任何预算 |
| D | `repository/sites.ts` `listSites` | 候选集一大就超参数上限 | `filterSiteIdsByFacets` 的结果被原样拼进 `s.id IN (...)`，参数个数由**数据量**决定 |
| E | `repository/sites.ts` + `search.ts` | 延迟随分面键数线性增长 | 每个键一条语句且**串行 await**；同一套分面交集逻辑还有两份独立实现（口径还不一致，只有其中一份做归一化） |

动手前先查证上限，因为分片大小要按最坏的构建而不是本机的构建来定：本机 better-sqlite3 13.0.3 + SQLite 3.53.4 从 1000 一路加到 **33000 才首次 `too many SQL variables`**（上限 32766），但 `SQLITE_LIMIT_VARIABLE_NUMBER` 在旧构建里默认 **999**，PostgreSQL 硬上限 **65535**。另外确认两件事：`DbAccessGate` 是读写锁，并发**读**合法（所以条件之间可以 `Promise.all`，不会和写事务争锁）；`toPgSql` 按 `?` 出现顺序重写为 `$n`，参数顺序即占位符顺序，分片拼接不会错位。

处置分四层：

1. **`packages/store/src/sql-in.ts`（新）**：`SQL_IN_CHUNK = 500`（沿用仓库里 `getSitesByIds` 已有的分片尺寸，不引新常数）、`chunkList`、`inPredicate`。关键约定：**`inPredicate` 一次只生成一片**。文件头注释点名那个假分片反模式——把 `(id IN (…500…) OR id IN (…500…))` 塞进同一条语句「看着像分片，参数总数一点没减，等于没分片」。第一版实现正是这样写的，被参数预算测试打回后才改成多语句归并（今天按第一版重跑了一次：`expected 602 to be less than or equal to 503`——见 §10.5.5）。
2. **`listSites`**：候选 ≤ 一片时走原来的单条语句（`ORDER BY`/`LIMIT`/`OFFSET` 交给 SQL）；超过一片时每片**只取排序键和 id**（窗口 `offset + limit`），在 JS 里归并排序再切片，整行由已分片的 `getSitesByIds` 取。分页语义不变——测试用 600 个站点（`sort` 打乱）逐条比对「分片归并后的前 50」与「全量排序后切片」。
3. **两份分面实现统一**：`filterSiteIdsByFacets` 与 `search.ts` 的 `siteIdsWithFacets` 都改成「条件之间并发、条件之内值分片、JS 交集带 early break」，值统一 trim + 小写 + 去重（原先只有一份做）。顺带修掉一处 shadowing：`getSitesByIds` 里局部的 `const chunk` 与新helper同名，已随 `chunkList` 重命名消掉。
4. **API 层预算 `clampFacets`（`routes/shared.ts`）**：键 ≤ `FACET_MAX_KEYS`(20)、每键值 ≤ `FACET_MAX_VALUES_PER_KEY`(200)、非纯量值（对象/数组/null）直接 400、非法 JSON 明确报「facets 必须是合法的 JSON 对象」；键与值统一归一化。`/api/sites`、`/api/search` 的 GET 与 POST 三处入口全部改用它，非法输入从「静默降级 / 悄悄变形」变成 400 + `detail` 写明原因。

回归：`packages/store/test/sql-in-budget.test.ts`（3 例：超一片时分页等价且单语句参数 ≤ 预算；单键 1001 个值自动分片；多条件确实并发）、`apps/api/test/facets-input-budget.test.ts`（6 例：坏 JSON / 超键数 / 超值数（GET 字符串与 POST 体两个分支）/ 检索侧同口径 / 非纯量 / 预算内正常过滤并验证归一化）。两个测试都通过包装 `repo.raw` 记录**每条语句的实际参数个数与并发峰值**，断言的是行为而不是实现细节。

### 11.4 自我更正：本轮撤回的两条候选结论

1. **`vendor-web.mjs:157-163`「递归删 `node_modules` 会穿过 pnpm junction 毁掉工作区源码」——本机实测不成立。** `lstatSync` 把 Windows junction 报成 `isSymbolicLink()=true`，Node 的递归 `rmSync` 对 symlink 只 unlink 不下降：构造 `HOST/node_modules/link → REAL-SOURCE` 后递归删 HOST，`REAL-SOURCE/keep.txt` 与 `REAL-SOURCE/sub/deep.txt` 均完好。2026-10-19 的事故出在 PowerShell `Remove-Item -Recurse` / .NET `Directory.Delete`（它们确实跟随 junction），那条铁律照旧适用于 PowerShell 路径，但不能拿它给 Node 侧的 `rmSync` 定罪。脚本因此**不改动**。

## 12. 2026-10-22 上午第七轮：MCP 契约兑现、运维入口的破坏半径，与「默认 100」造成的静默截断

前六轮覆盖了 API、存储、部署配置、AI 容错与 `scripts/` 门禁。本轮扫的是三类**没被任何前轮覆盖**的面：`packages/mcp`（对外承诺的 schema 与处理器实现是否一致）、`docker/` + 运维入口（一次误操作能造成多大破坏）、以及数据治理与请求路径的性能。

本轮最大收获不是单个 bug，而是**一条贯穿性缺陷类**：`listSites()` 的默认 `limit 100`（`packages/store/src/repository/sites.ts:69-70`，注释写明「无限制的全表扫是慢查询主因」）是一道**性能护栏**，但六个「语义上必须全库」的调用点把它当成了默认读取方式。库小于 100 时一切正常，超过之后冷备少导、恢复重复插、热度榜不再更新、索引重建只覆盖前 100 条却报告成功——没有任何一处会报错。

### 12.1 【P0·已修复】运维脚本自己会打到生产库：`pg-check` 的 DSN 兜底

### 12.3 【P2·已修复】数据治理：`retention` 预览模式把自己跑满

`packages/store/src/retention.ts` 的 dry-run 只数不删，因此**没有推进游标**：`WHERE created_at < cutoff ORDER BY id LIMIT batch` 每批取到的是同一批行，`maxScan` 循环一路把 `scanned` 顶满、`batches` 虚高，预览报告里的「将归档 N 行」其实是对同一批行重复计数。另一处：dry-run 仍调用 `options.archive()`，**冷备文件里被写进了从未删除的数据**——下次 restore 就会把这些行复活。

修复：预览分支显式带 `AND id > cursor`（`retention.ts:145`），并且只在 apply 模式调归档回调（`:163`）；预览统计走 `result.archived += rows.length`（`:160`）不再产生文件。消融：去掉游标 → `scanned` 从 7 变 100000（顶到 `maxScan`）；去掉归档守卫 → `archivedRows.length` 从 0 变 7。`packages/store/test/retention.test.ts` 12 例覆盖两种模式的分歧点。

### 12.4 【P1·已修复】贯穿性缺陷：默认 100 条的静默截断

同一个根因，六个调用点。逐点修复原则：**要么走无上限的 `listAllSites(limit?)`，要么用一条聚合/瘦列 SQL 取全键**——`selectSitesSql()`（`sites.ts:157-165`）每行带两个相关子查询（tags、facets），全表整行读是没必要的重成本。

| 调用点 | 库超过 100 条后的真实症状 | 修复 | 消融（改回旧写法后变红的断言） |
|---|---|---|---|
| `GET /api/export/backup.json`（冷备） | 只导出 100 条，恢复时把「没导出的」当已删除 → **冷备即数据丢失** | `ctx.repo.listAllSites()` 无上限（`backup.ts:53`） | `backup-full-coverage.test.ts`：`expected 100 to be 131` |
| `GET /api/export/bookmarks.html`（公开） | 书签文件缺页 | 显式上限 `NAVHUB_EXPORT_MAX_SITES`（默认 20000，`backup.ts:19,30`）——公开入口**必须有**上限，但默认要大到导航库不可能触及 | 同上，`<A HREF=` 计数 100 vs 131 |
| `POST /api/backup/restore` | 去重集合只装了前 100 条 URL → 重复恢复撞唯一索引，**恢复中途返回 500，库里一半新一半旧** | 一次取全 `SELECT url FROM sites WHERE deleted_at IS NULL`（`backup.ts:103`） | 给去重查询加 `LIMIT 100` → 恢复接口 500（本表里唯一「500 级」的消融） |

### 12.5 【P1·已修复 + 提速】请求路径：`/api/sites/duplicates` 与 taps 同步

**`/api/sites/duplicates`**（1000×1000 双循环）旧写法每对站点都 `new URL()` 两次、`split(/\s+/)` 建 Set 做 Jaccard，而且 `Math.min(ta.size,tb.size)/Math.max(...)` 这个上界**先算出来再决定要不要跳过**——上界已经低于阈值时白建了两个 Set。重写为：每个站点预计算 host/小写标题/token 集合（O(n) 次解析），配对时用「标题集合大小比」做**先于任何 Set 分配的上界剪枝**，命中才真正算 Jaccard；输出顺序用 `(i,j)` 显式排序锁死，与改写前逐条一致。语义等价性不靠人眼：`apps/api/test/site-duplicates.test.ts`（5 例）内嵌一份**改写前实现的逐字副本**作参照，用固定种子 mulberry32 生成 600 站语料（含 `javascript:`、`file:///`、非法 URL、IDN、空标题），断言 `toEqual(reference)` 深相等；另有一条人工边界用例锁住「`github.com` vs `docs.github.com` + 同名标题 → 0.9」这类容易被「优化」掉的细节。

速度声明也做了非空消融：把预计算/剪枝复原后，同一断言里 `fast`(优化后) 18.5s vs `slow`(旧写法) 6.2s → `expect(fast * 3).toBeLessThan(slow)` 变红；参照实现带 memo（`refCache`）以免 O(n²) 被重复跑（36.7s → 13.1s）。同时新增 `truncated` 字段（`packages/core/src/types.ts` 的 `SiteDuplicateReport`）：达到 2000 对上限时**必须说出来**，否则调用方会把「截断结果」当「全站查重结论」。

**`POST /api/plugins/taps/:id/sync`** 两处：
1. 去重是**每条跑一次** `listPlugins({ q: name, limit: 5 })` 再要求精确同名。这既是 N 次走不到索引的全表 `LIKE`，又是正确性缺陷：`plugins.name` **没有唯一索引**（只有 `plugins_slug_idx`），同名条目一旦被 5 条窗口挤出就漏判，市场里出现成对同名插件（`createPlugin` 的 `uniqueSlug` 还会给 slug 加 `-2`，把重复伪装成两个合法插件）。改为一次 `SELECT name FROM plugins` 建集合、精确匹配，并在同一份清单内部也查重（原实现只是「每条查库」时碰巧挡住）。
2. 远端清单长度是**外部输入**，每条都要写库 + 向量化：一个 10 万条的订阅源能把单个请求变成几小时的后台任务。加 `NAVHUB_TAP_IMPORT_MAX`（默认 500，`plugins.ts:51,1646`）并在响应里如实返回 `fetchedCount` / `importedCount` / `truncated`。

消融（`apps/api/test/tap-sync-import.test.ts` 3 例，`vi.mock("@navhub/ai")` 只替换 `guardedFetch`）：把去重复原成「`listPlugins({q, limit:5})` + 无批内去重」→ 跨窗口那条用例 `expected 1 to be 0`（真的多插了一行）；去掉上限 → `expected 8 to be 5`。两次消融各自只让对应维度变红，其余保持绿，说明三条断言分别咬住三件事。

### 12.6 【P2·已修复】`scripts/d1-regression.mjs`：自称 PASS，却删掉用户的真实内容
