## 1. 执行摘要

项目不是需要推倒重来的早期导航模板，而是一个已有大量自研能力、较成熟工程治理的中大型 monorepo。当前最重要的工作不是盲目增加功能或重写架构，而是：

1. 先恢复并稳定 CI 的可信绿灯；
2. 将真实用户旅程、商业转化、国际化和内容质量作为产品主线；
3. 在既有 API、存储、权限、主题和组件体系内渐进演进；
4. 用可复现证据验证每项改动，避免只增加文档、开关或“看起来完成”的功能。

## 4. 当前阻塞与风险（有证据的事项）

### P0：CI 尚未形成可信绿灯
最近可见的 main CI 运行（2026-11-23，run 45114187627）总体失败。已读取作业结论：
- 成功：前端 typecheck/lint/build、PostgreSQL 跨方言测试、SQLite 三个分片中的 1/2/3、Playwright 分片 2/2、镜像冒烟构建、overlay/扩展规范检查、依赖审计、覆盖率门禁。
- 失败：ISR 线上抽查作业中的“ISR 线上抽查”步骤；Playwright E2E 分片 1/2 的测试步骤及红灯台账步骤；聚合门禁因此失败。
- 最近一次 video-harvest workflow（2026-11-23）也失败。
- 当前存在 Dependabot PR #105、#106、#107、#97；前三个近期依赖升级 PR 的 CI 运行有失败记录。

**根因已从 GitHub Actions job 日志确认：**

1. **ISR 首页 SEO 契约失败（代码问题）**：14 个抽查页面只有首页 `/` 失败，实际 HTML 有 2 个 `<h1>`，门禁要求恰好 1 个。sitemap 有 575 条，站点详情/分类/标签/合集/插件/目录族计数均达到配置下限，lastmod 覆盖 532/575（93%），其余抽查页面通过。根因是移动端品牌标题在 `navigation-content.tsx` 中又使用了一个 `h1`，而侧边栏品牌标题已经提供唯一语义 H1。
2. **Playwright E2E 失败（测试口径漂移）**：`e2e/exam-node-links-u124.spec.ts` 的 `NON_PRINT_LABELS` 只有 5 个例外，实际渲染层和 Vitest 已有 10 个例外；因此测试预期 18 个「去官网打印准考证」，真实数量为 13。失败点在 E3 断言，业务数据和 URL 不需要变更。
3. **视频采集定时 workflow 失败（仓库环境配置问题）**：`video-harvest` 在发起请求前即因缺少 `secrets.NAVHUB_SITE_URL` 退出；同一工作流也要求 `secrets.CRON_SECRET`。这不是采集器解析器故障。应由仓库管理员在 GitHub Actions Secrets 中补齐正确生产地址和服务端 cron 密钥，不应将密钥写入代码、PR 或日志。
4. **PR 内部链接门禁（工具安装步骤问题）**：`links-pr` workflow 下载归档时将文件保存为 `/tmp/lychee.tar.gz`，但官方 SHA256 文件引用的文件名是 `lychee-x86_64-unknown-linux-gnu.tar.gz`；`sha256sum -c` 因文件名不匹配在 lychee 启动前退出。此问题同时影响 PR #108 与 PR #109，不是文档死链。
5. **E2E 作业里的隔离用例**：日志另有 `@quarantine` 过滤结果为 No tests found；该步骤本身被设计为不阻塞合并，主阻塞失败是 U-124 E3 的 18 vs 13 断言。

**行动与状态：** 已在独立 PR #109 修复前三项代码/测试/工作流问题：移动端重复 H1 改为视觉段落；E2E 特殊文案列表补齐 10 项；lychee 下载文件名与 SHA256 清单统一，保留原校验。未修改考试业务数据、外链 URL 或 CI 门禁。视频采集缺密钥需仓库管理员补齐 Actions Secrets。PR #109 新 CI 正在运行，尚未宣布通过。

### P1：产品商业化验收缺少统一“可上线”定义
README 声明账号、会员/商业化构想、管理后台和 API 能力，但项目尚标注为未正式上线。需要建立统一验收矩阵，明确：
- 用户旅程：首次访问、搜索、详情、收藏、注册、登录、跨设备同步、反馈、留存。
- 运营旅程：提交收录、审核、批量导入、失效巡检、内容治理、用户支持。
- 商业旅程：套餐/权益、订单、支付回调、退款/对账、广告位审核、发票/税务（按目标市场适用）。
- 运营安全：滥用防护、速率限制、审计、数据导出/删除、隐私同意与保留周期。
以上是待验收项，不代表仓库当前全部缺失；必须先对照现有代码盘点，禁止重复造轮子。

### P1：国际化与全球分发需要以运行态验证
项目目标是全球用户，但“多语言、国家推荐、地区适配”应有可验证标准：语言覆盖与回退、时区/日期/数字格式、国家/地区信号来源及隐私、搜索结果地域相关性、外链可达性、区域内容合规、SEO hreflang/canonical、移动网络性能。先检查已有实现与真实页面，再决定补齐范围。

### P1：站点与视频内容质量是核心资产风险
大量收录本身不等于高质量。需定义 URL 规范化、重复站点/镜像识别、站点健康状态、内容来源/版权与更新策略、恶意站点/钓鱼举报、分类置信度、失效恢复和审核 SLA。视频内容需独立检查来源授权、可用性、重复率、地区可访问性和下架机制。

### P2：规模增长后的可观测性和成本治理
应以真实生产指标建立 SLO：首页/搜索 p50、p95、p99，API 错误率，SSR/ISR 命中率，数据库慢查询，队列积压，采集成功率，Embedding/LLM 单次成本，缓存命中率和用户关键转化。已有日志、健康检查或指标模块应优先复用。

## 6. 本轮执行纪律

1. 不直接向 `main` 提交；所有改动先在独立分支与 PR 中审查。
2. 不大规模重写，不移除现有功能，不改动未经核实的事实源数据。
3. 前端只改 `apps/web-overlay`，并按仓库既定流程生成/检查 `apps/web` 镜像。
4. 涉及数据库时同时考虑 SQLite/PostgreSQL、迁移、回滚、备份和数据保留。
5. 新功能必须有单元/集成/E2E 测试、权限策略、REST 契约和文档登记（按现有仓库门禁要求）。
6. 禁止将测试 skip、阈值下调、台账延长 TTL 或忽略告警作为修复。
7. 每批改动只解决一个可验收主题，报告变更文件、测试命令、结果和未验证项。
8. 任何线上配置、密钥、真实用户数据、支付/邮件发送和生产部署操作，均不得在没有明确授权与安全验证时执行。

## 8. 审计结论

当前代码库已有相当多的工程基础，不能把“商业级”理解为堆叠更多功能。真正的升级顺序应是：**先确保发布门禁可信，再确保关键用户旅程稳定，然后提升内容质量、全球体验和商业闭环，最后用 SLO 与成本数据支撑规模化运营。**
