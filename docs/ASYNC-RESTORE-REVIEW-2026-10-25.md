# 异步恢复方案 · 深度审阅与后续行动（2026-10-25）

> 审阅对象：`docs/ASYNC-RESTORE-DESIGN.md` 及其落地代码（`apps/api/src/routes/backup.ts`、
> `apps/api/src/jobs.ts`、`packages/store/src/repository/sites.ts`）。
>
> **一句话结论**：方案结构是标准的 Asynchronous Request-Reply 模式，落地完整、可用；
> 但它最核心的安全论证——「幂等性可以兜住分片的原子性」——**在任务重试这条路径上不成立**，
> 会产生重复站点行。这不是理论风险：`MAX_JOB_ATTEMPTS = 3` 且 `insertSitesBulk` 是裸
> `INSERT INTO sites`，`sites.url` 上没有唯一约束，所以重复写入既不会报错也不会被拦下。

| 层 | 设计 | 落地 | 评价 |
|---|---|---|---|

## 3. 核心目标达成度

| 目标（§1.3） | 达成 | 证据 |
|---|---|---|
| 1. 不再占用 HTTP 请求时长 | ✅ | 请求内只做校验/算计划/写 staging；实测 1 万条预演 388ms |
| 2. 调用方能看到进度 | ✅ | `progress_done` / `progress_total` + 前端进度条 |
| 3. 失败可归因，**且不留半套数据** | ❌ | 与分片方案**直接矛盾**——分片的前提就是「失败时可能留下前几片」。见 §5 R1 |
| 4. 与同步端点共存 | ✅ | 同步端点未改，前端按阈值择一 |

> 目标 3 是文档里最危险的一句：它是选分片之前写下的，选了分片之后没有回头改。
> 后来者照这条目标验收，会把「留下前几片」判成 bug，或者反过来以为不该留下。

## 5. 风险清单

### P0

**R1b · 任务重试会在第一个分类就失败（实施时才发现，比 R1 更早触发）**

- 触发：任何带分类的备份，第一次执行中途失败 → 自动重试 → `runBackupRestore` 重新走 `createCategory`。
- 后果：`createCategory` 先做同级同名检查（`assertNoSiblingTitleClash`），第二次必然抛
  「同级下已存在名为 X 的类目」。于是 **3 次尝试里后两次全部卡在第一步**，站点写入根本不会发生；
  用户看到的是「重试三次后失败」，但报出的原因与真实的第一次错误完全不同，排查方向会被带偏。
- 证据：`packages/store/src/repository/categories.ts:117`（同名检查）与 `:172`（裸 INSERT）。
- 副作用：它**掩盖了 R1**——重试在写站点之前就死了，重复行反而不容易出现。
  这也说明「重试幂等」必须先于「站点去重」修，否则改了后者也验证不到。
- 已修：按 id 跳过已存在的分类。

**R1 · 任务重试会重放已提交的分片，产生重复站点行**

- 触发：任务在第 N 片抛错 / 超时 / 进程被杀 → `status=retrying`（`MAX_JOB_ATTEMPTS=3`，退避 1/2/4 分钟）→ 重新认领 → 从 `i=0` 重放。
- **后果（2026-10-25 修正）**：前 N-1 片再插一遍，会撞 `sites_url_idx`
  （`CREATE UNIQUE INDEX ... ON sites(url) WHERE deleted_at IS NULL`，由 `migrateSiteIndexes` 建）
  → 整片 `UNIQUE constraint failed` → 事务回滚 → 任务再次失败 → 3 次耗尽落 `failed`。
  **不是**本文件初版写的「静默插入重复行」——那条判断是错的，已实测确认索引存在。
- 所以真实症状是「**重试永远不会成功**」，报错是 `duplicate_key`；初版把它写成了
  「用户看到重复卡片」，会把人引向完全错误的排查方向（去查 UI 去重而不是查约束）。
- 证据：`packages/store/src/migrate.ts:183` `migrateSiteIndexes`；实测新建库的
  `sqlite_master` 里确有该索引。
- 已修：每片写入前用 `findExistingSiteUrls` 过滤（A1）——重放从「撞约束失败」变成「全部跳过」；
  并从 `progress_done` 续跑（A4）。**注意：修复的价值在于让重试有效，而不是防重复行。**

**R2 · 僵尸回收 + 重放 → 并发写**（H4 与 R1 耦合）

- 触发：任务超过 15 分钟仍在跑 → `reapStaleJobs` 认为它死了 → 另一个 worker 认领同一 job。
- 后果：两组分片**同时**写入；叠加 R1 的重放，重复量翻倍，且两组写入互相干扰。
- 这是「分片」+「无幂等」+「无并发守卫」三件事叠出来的，任何一件补上都能降级。

**R3 · 文档与代码 8 处不符，其中一处是目标级矛盾**

最危险的已列在 §3（目标 3）。其余：`§1.4` 声明「不改前端」但前端已做；`§6` 的 `asyncRecommended` 从未实现（实际是前端按阈值切）；`§7` 描述的是旧设想（2 秒轮询/跳转 sitelist），实际是 1.5 秒/转后台/不跳转；`§2.1` 的 `stagedBytes` 与 `?dryRun=false` 参数都不存在；`§4` 代码签名已变（`(payload, jobId)`）；`§8` 第 6 条仍写 `completed`、第 7 条仍写「非发起者 404」（实际是 admin scope 拦截）。

### P0（实施 A11 时新增，已修）

**R13 · `getSite` 的 OR 查询让「重建索引」变成 O(n²)**

- 现象（由基准牵出）：10k 站点的 `reindex` 要 47.7 秒，而恢复本身只要 1.7 秒。
- 根因：`getSite(idOrUrl)` 写的是 `WHERE (s.id = ? OR s.url = ?)`。OR 跨两列，
  SQLite 用不上主键索引，退化成**扫整个 `sites_url_idx`**（`EXPLAIN` 显示
  `SCAN ... USING INDEX`，而不是 `SEARCH ... (id=?)`）。单次 5.8ms × 每个站点 ×
  `updateSite` 内部也调它 → O(n²)。
- 影响面远超恢复：`getSite` 有 94 处调用（详情页、编辑、任务），万行库上每次单站读取
  都要 5.8ms；5 万行时约 29ms。
- 已修：拆成「先按主键，未命中再按 url」。实测 `reindex` 47.7s → **3.97s**（12 倍），
  `getSite`×10000 58.2s → 4.6s，`updateSite`×10000 41.6s → 4.3s。
- 附带结论：默认分片大小从 2000 改为 **1000**（实测 10k 快 22%、30k 快 39%）。

### P0（实施 50k 压测时新增，已修）

**R14 · 大包在「到中枢之前」就被拦掉了：BFF 1MB + 全局 4MB，而声明上限是 50k**

- 实测体积：约 **187 字节/站点**。于是
  - BFF 代理（`/api/hub/*`）的 `MAX_BODY_BYTES = 1MB` → 只够 **约 5,400 条**；
  - 中枢全局 `bodyLimit: 4MB` → 只够 **约 2.1 万条**；
  - 而 `RESTORE_MAX_SITES = 50_000`（5 万条约 **9.27MB**）。
- 后果：页面在「预演算出 >5000 条」时才转异步——**这个分支在界面上几乎永远走不到**，
  因为 5,000 条以上的包会先被 BFF 以 413「请求体过大（上限 1MB）」拒掉。
  异步恢复这条链路此前只在测试与 curl（直连中枢）里成立。
- 业界并不奇怪：网关/代理的 body 上限默认值本来就比业务上限小，两端必须对齐。
- 已修：BFF 对 `backup/restore*` 单独放宽到 **16MB**（其余接口仍 1MB）；
  中枢两个恢复端点路由级 `bodyLimit` 也到 16MB（全局仍 4MB）。
- 验证：一份 **6MB+**（3.5 万条）的备份包现在返回 202，此前会被 413。

### P1

**R4 · 后端没有并发守卫**：只在前端禁用了文件输入。两个 admin（或绕过 UI 的 curl）同时提交 → 交错写入。
**R5 · 两处 URL 归一化口径不一致**：`planRestore` 用 `replace(/\/+$/,"").toLowerCase()`，`findExistingSiteUrls` 用 `canonicalizeUrl()`（还会探测带/不带斜杠的两种形态）。同一 URL 在两处可能得出不同的「是否已存在」。
**R6 · 契约缺 `Location` 与 `Retry-After`**：行业标准（Microsoft API 指南、OpenAPI 异步模式）要求 202 带 `Location` 指向 status 资源，并用 `Retry-After` 让服务端指挥轮询节奏。当前只有 body 里的 `statusUrl`，客户端节奏写死 1.5 秒。
**R7 · staging 被 sweep 删掉后，job 仍报 `retryable: true`**：超过 24 小时的失败任务重跑时读不到 staging → 必失败，但状态说「可重试」。
**R8 · 没有取消通道**：整库写操作一旦提交无法中止，只能等它跑完。

### P2

**R9 · 零增量时仍创建任务**：备份里全部条目都已存在 → `total=0` → 前端进度文案停在「正在准备恢复计划…」，然后才报「成功恢复 0 个站点」。
**R10 · 前端轮询无退避、无上限**：长任务（PG 下可能十几分钟）会持续每 1.5 秒打一次。
**R11 · 分片大小 2000 是拍的，没做过基准**（见 H3）。
**R12 · staging 默认相对路径**（H5），容器部署易踩。

## 6. 可行性评估

- **已实现部分的可行性：高**。契约、载荷、进度、前端都跑通并有测试；异步化确实解决了原本的问题（请求时长与数据量解耦）。
- **薄弱环节的共性**：方案把「正确性」押在了**幂等**上，而幂等只在**一次请求的边界内**成立；一旦跨越「任务重试 / 并发 / 时间窗口」这三个边界，它就失效了。三处薄弱（R1/R2/R4）本质都是同一件事：**缺少一个跨边界的、写入时的幂等或互斥保证**。
- 好消息：所需的原语仓库里**已经存在**（`findExistingSiteUrls(repo, urls)`、`jobs` 表查询、`progress_done`），修复不需要新建机制。

| **A11** | ✅ | 分片基准脚本 `scripts/bench-restore-chunk.ts`（事件循环延迟探针、每配置独立空库、只计恢复自身） | P2 | 无 | 用实测替换估值；顺带挖出 R13 | 10k：1000→2.49s / 2000→3.21s / 5000→3.56s；30k 同序 → 默认值改 1000 | 中 |
| **A12** | ✅ | 收尾 reindex 按需：0 条不入队、≤5000 条增量（只重建本次写入的 id）、断点续跑强制全量 | P1 | 需 `runReindex` 支持 `siteIds`（已加，分块 500） | 5 万库补录 100 条从 66s 降到 0.19s（350×） | 4 例：增量带 id、零增量不入队、续跑转全量、`siteIds` 只处理指定站点 | 中 |

### 实施 A10 时发现的额外缺陷（值得单独记）
`better-sqlite3` 是**同步**驱动，而任务循环在整片（2000 条，数秒）内不让出事件循环。
后果不只是「取消进不来」，还包括**前端进度查询被整段阻塞**——那不叫慢，
是进度条真的不动。修复是在每片开头 `await new Promise(r => setImmediate(r))`。
这条约束对「进度上报」和「取消」是同一件事：**任何长循环都必须周期性让出事件循环**，
否则同一个进程里的 HTTP 全部停摆。

> A1 的一处实现取舍：`progress.done` 记的是**已处理条数**（分片偏移），不是实际插入数。
> 因为断点续跑要对齐分片边界，而这两者在正常情况下相等（计划已按现有 URL 过滤）；
> 只在并发插入或重放时才会差一点。为此前端文案从「已写入 N 条」改成「已处理 N 条」，
> 失败说明里保留「已写入的那部分会保留」——既不漏报也不虚报，且不必为此再加一列。

## 8. 执行顺序（前三批已完成）

```
第一批（已完）
  A1 分片写前去重 + 分类幂等  ← 必须先做：否则重试死在建分类，站点去重根本跑不到
  A2 后端并发守卫
  A3 文档修订

第二批（已完）
  A4 断点续跑      ← 依赖 A1（否则续跑仍可能重插）
  A5 归一化统一    ← 与 A1 同文件区，排在其后避免冲突
  A7 sweep 保护

第三批（已完）
  A6 Location/Retry-After ──→ A9 前端退避与上限（A9 依赖 A6）

第四批（未做）
  A10 取消通道    ← 已完：复用 status='cancelled'（completeJob 的 CAS 已能保住终态）
  A11 分片基准    ← 要先有 5 万条生成脚本
```

**实施时的顺序修正**：原计划把 A1（站点去重）放在最前，实际动手时发现**分类幂等同批必须一起改**
——`createCategory` 的同类目同名检查会让重试在写站点之前就失败，只改站点去重根本验证不到。
所以第一批实际是「A1 + 分类幂等」两件事绑在一个改动里。

**为什么 A1 值得排最前**：它同时修掉 R1（重试重放）、R1b（分类撞名）、R3 的一部分
（预演→执行的时间窗口），并给 R2 兜底。改动只有几十行，但它是整个方案里唯一
「正确性依赖一个未成立的假设」的地方。

## 9. 明确不建议做

| 不做 | 理由 |
|---|---|
| 给 `sites.url` 加唯一索引 | 库里存在软删除的同 URL 行，加索引会让恢复直接撞约束失败，也会破坏 `findExistingSiteUrls` 只认 `deleted_at IS NULL` 的既有语义。用写入时过滤替代（A1） |
| 改回单事务求原子性 | 单事务持写锁数十秒是可用性问题，且大事务回滚成本高。分片方向是对的，缺的是幂等 |
| 断点续传（跨进程续跑未提交片） | 恢复本身能在几十秒内重跑完，续传的复杂度不值。A4 的「从已提交片之后继续」已经是够用的折中 |
| 引入 SSE / WebSocket 推进度 | 轮询在这个场景（分钟级、单一调用方）够用；A6 的 `Retry-After` 已能解决节奏问题。引 SSE 要动 BFF 的压缩与代理配置（记得 `/api/hub/*` 会解压重发），收益不抵 |
