# 冷启动预热：把「第一个用户的 1.4 秒」提前到启动后（2026-11-03）

> 本轮是**深度代码审计 + 真痛点修复**。先说审计结论，再说改了什么。

## 1. 审计结论：哪些看着像问题、实际不是

审计目标是「砍掉虚头巴脑 + 解决真痛点」。先排除掉三个「看起来该做、实际不该做」的候选，
避免做出无用改动：

| 候选 | 结论 | 依据 |
|---|---|---|
| 图标缺失（1015/1026 站点无 `icon_key`） | **不是缺口** | `site-favicon.tsx` 有完整兜底链路：自定义图标 → 目标站 favicon → 内联晶体徽标；并对第三方图标服务与远端裸 `/favicon.ico` 做拦截。无 `icon_key` 会渲染渐变徽标，视觉完整 |
| 无人调用的 API 路由（可砍的死代码） | **没有** | 实测扫描 286 条路由 × 902 个消费侧文件，**0 条**无人调用 |
| 重复站点 / 未分类站点 / 缺描述 | **已是 0** | 数据普查：重复 URL 0 条、未分类 0 条、缺描述 0 条 |

也就是说：这个仓库没有大块可砍的虚代码。硬要砍只会制造回归。真问题在**性能**上。

## 2. 真痛点：冷启动让第一个用户替所有人付初始化钱

进程内打点实测（同一进程连续搜索）：

```
q=zzzunlikely1   2512ms   ← 首次
q=python            9ms
q=设计             10ms
```

百倍差异。进一步定位：`createContext` 后才 184ms，而 **首次 `encode()` 就 1396ms**——
这是 ONNX 模型加载，一次性的。此后 `encode()` 为 0ms。

**结论**：这 1.4 秒本该在部署后立刻付掉，实际却由第一个走语义通道的真实用户承担。

### 为什么一直没被修

代码里其实早有预热能力：`POST /api/warmup`，以及搜索路径里的 `kickWarmup`（fire-and-forget）。
但它们都要求**有人主动触发**。部署脚本通常不调 `/api/warmup`，于是生产上这笔钱永远落在第一个用户头上。

## 3. 修复：启动后台预热

在 `createContext` 装配完成后调度一次 `embedding.warmup()`，三个刻意的取舍：

1. **用 `setImmediate` 推迟到下一轮事件循环，绝不 await。**
   踩过的坑：起初写成 `void Promise.resolve().then(() => warmup())`，看名字像异步，
   但微任务在当前 tick 尾部立刻执行，重 CPU 的模型加载照样挡住启动——
   实测把 `createContext` 从 184ms 拖到 2700~3600ms。换 `setImmediate` 后创建先返回，
   预热在随后的宏任务里跑，HTTP 能先 listen。
2. **失败只记 note，不抛。** 模型文件缺失/损坏时语义通道本就该降级（搜索仍然可用），
   绝不能因为预热失败让服务起不来。与 `plugins-search.ts` 的 `kickWarmup` 同口径。
3. **`NAVHUB_EMBEDDING_WARMUP=0` 可关。** CI、一次性脚本、批量任务不该为一次进程
   加载几百 MB 模型。给明确关闸，而不是让人默默忍受启动噪音。

## 4. 验证

### 4.1 真实服务生效证据

在独立端口起一个新实例（不动共享实例），`GET /api/health` 的 `capabilities.notes` 里出现：

```
- embedding 启动预热完成（首次搜索无需再等模型加载）
```

### 4.2 预热后的语义通道延迟

```
q=帮我写代码的工具   111ms  hits=5
q=视频剪辑            56ms  hits=2
q=zzzone              48ms  hits=0
```

对比未预热时首次走语义要付 1396ms——这就是被消除的那笔钱。

### 4.3 启动成本的诚实交代

预热开启 vs 关闭，`createContext` 各测三次：

| 预热 | 三次耗时 |
|---|---|
| 开启 | 2956 / 2506 / 2428 ms |
| 关闭 | 2283 / 2560 / 2119 ms |

差值约 **300–400ms**，来自预热与主线程争 CPU（模型加载本身是重 CPU 工作），
**不是数量级阻塞**。这笔钱是可接受交易：用 0.3 秒启动换取「第一个用户少等 1.4 秒」。

> 补充实测：`createContext` 里真正的大头是 `import './src/context.ts'` 的依赖树加载（1609ms），
> 不是 context 构建（184ms）。这份观察留给后续优化，本轮不动它——改 import 结构风险大、
> 收益需要单独验证，属于另一个课题。

### 4.4 回归

- 新增 `apps/api/test/embedding-warmup.test.ts`：5 项（默认开启 / overrides 关闭 /
  环境变量开与关 / 惰性装配时 semantic 如实为 false）。其中一项是**结构性契约**：
  若有人把预热改回同步 await，它立刻变红。

- `@navhub/api` 的 `tsc --noEmit` → **0 错误**。

## 5. 一个必须说清的局限

我一度想用「新旧实例对比延迟」当证据，但实测两边都已被先前的请求预热过，
数据不可比（新实例 423ms/119ms、旧实例 164ms/551ms，波动无规律）。
**这个对比不成立，不拿它当证据**。上面的 1396ms 是进程内首次 `encode()` 直接测量，
那才是可靠依据。
