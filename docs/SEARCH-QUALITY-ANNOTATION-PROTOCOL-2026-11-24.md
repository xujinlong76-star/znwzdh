# 搜索质量金标集标注与上线闸门

> 本文是搜索质量评测的操作规范。当前仓库已有离线评测函数与少量 golden fixtures；扩充相关性标签必须来自真实查询和人工判断，禁止用模型自评或合成标签冒充金标。

## 1. 当前状态与目标

- 已有指标：NDCG@K、MRR@K、Recall@K，见 `packages/core/src/search-eval.ts`。
- 已有执行入口：`scripts/search-eval.mts`。
- 现有 golden fixture 数量有限，不能据此宣称覆盖全球、多语言或所有导航类目。
- 第一阶段目标：至少 100 条去标识化查询；每条查询至少 2 名标注员独立标注；分歧由第三人仲裁。
- 覆盖面目标：中文、英文、拼音、混合语言、错别字、精确站名、功能意图、类目意图、零结果、歧义查询和长尾查询。

## 2. 查询样本抽样

从真实搜索遥测中按意图分层抽样，而不是只取高频词：

| 分层 | 建议占比 | 说明 |
|---|---:|---|
| 精确站点/品牌名 | 15% | 用户明确寻找某个站点 |
| 功能/任务意图 | 20% | 例如“在线压缩图片”“生成流程图” |
| 类目/主题意图 | 15% | 例如“AI 视频工具”“开源数据库” |
| 拼音/输入错误 | 15% | 拼音、首字母、错别字、空格差异 |
| 英文/混合语言 | 10% | 英文查询、中文夹英文 |
| 零结果/低点击 | 10% | 重点检查召回缺口 |
| 歧义/长尾 | 15% | 多意图、低频但有明确任务的查询 |

隐私要求：
- 不导出登录身份、邮箱、IP、token、原始 userId/anonId。
- 可能包含个人信息的 query 必须先脱敏；无法可靠脱敏的样本不进入标注集。
- 只保留评测所需的 query、语言/意图标签、候选 siteId 和快照时间。
- 生产查询日志只用于抽样，不自动转成 relevance 标签。

## 3. 相关性等级（0–3）

| 等级 | 定义 | 判断标准 |
|---:|---|---|
| 0 | 不相关 | 与查询意图无关、站点不可用或无法完成任务 |
| 1 | 弱相关 | 主题相近，但无法直接完成主要任务 |
| 2 | 相关 | 能完成主要任务，但不是最匹配的结果 |
| 3 | 高度相关 | 与用户意图高度一致，是明确的优先选择 |

标注时必须查看站点实际落地页或可靠的站点元数据；不能只根据域名、标题或 AI 生成描述打分。无法访问时标记 `unjudgeable`，不要自动标成 0。

## 4. 双人标注与仲裁

1. 标注员 A、B 独立标注，互相不可见对方结果。
2. 对同一 query + siteId 的等级差异大于 1，必须进入仲裁。
3. 对“不可判断”与“0 分”严格区分。
4. 记录标注员、标注时间、证据 URL、理由码；对外评测报告只发布聚合指标。
5. 每轮抽取至少 10% 样本做一致性复核；一致性明显下降时暂停扩充并修订指南。

## 5. 评测口径

每次排序变更必须使用同一份冻结快照，分别计算：

- NDCG@5 / NDCG@10：衡量高相关结果是否靠前。
- MRR@10：衡量第一个相关结果的位置。
- Recall@10：衡量前 10 条是否覆盖已知相关站点。
- 零结果率、可评估候选覆盖率。
- P50/P95 搜索延迟、索引/数据库负载。

建议发布闸门（初始值，需由业务负责人确认）：
- NDCG@10 相对基线提升至少 2%，或在不下降的前提下有明确业务收益。
- Recall@10 不得下降超过 1 个百分点。
- P95 延迟增幅不得超过 10%。
- 高风险候选不能因质量分而被提升；证据不足候选不参与重排。
- 分语言、分意图、分类目报告，不能只看宏平均掩盖局部退化。

## 5.1 评测报告隐私与诊断口径

`scripts/search-eval.mts` 的终端与 JSON 报告只输出 `queryIndex`，不输出原始 query 文本，避免 CI 日志、工单附件或评测报告意外扩散查询内容。评测诊断额外统计：
- 零结果查询数；
- 没有正相关标注的查询数（需区分“尚未标注”与“人工确认全部不相关”，不得将其解释为排序失败）；
- 已标注相关候选总数、Top-K 找回数及微平均覆盖率；
- 每条样本的 1-based 行号和计数，不包含 query 文本。

既有 NDCG/MRR/Recall 宏平均口径保持兼容；诊断统计不能替代人工标注，也不能把“没有正相关标签”自动推断为“没有相关站点”。如果评测文件需要留档，原始 query 应留在受控数据存储中，报告只保存脱敏样本 ID/行号及聚合指标。

## 6. 质量影子重排实验

线上搜索链路对约 10% 的查询做确定性采样：批量读取前 20 条候选的质量快照，计算影子名次并记录 baseline/shadow siteId 对照。遥测只存查询 SHA-256 摘要、长度和排序统计，不重复保存原始查询文本或用户身份；读取/写入失败不会影响搜索响应。生产返回结果仍使用原始融合排序。
## 7. 影子重排离线评测

已有人工标注与冻结候选快照后，可使用新增 CLI 对比原始排序与质量影子排序：

```bash
node scripts/search-quality-shadow-eval.mts path/to/shadow-fixture.json --json
```

输入 schema 为 `search-quality-shadow-v1`，每条 case 包含：
- `query`：脱敏后的真实查询；
- `baselineHits`：同一候选快照下，生产融合排序的 siteId 顺序；
- `relevance`：人工审核的 0–3 相关性等级；
- `qualityBySite`：同一快照时点的质量分、证据覆盖率和质量分档。

缺少质量快照的候选会按“未知/证据不足”处理，不会被质量分提升。脚本输出 baseline/shadow 的 NDCG、MRR、Recall 和差值，并统计移动数量、实际应用质量分数量及被排除数量。该 CLI 只读本地文件，不访问生产数据库，也不会更改线上搜索排序。

## 8. JSONL 标注记录格式

每行一条 query，字段参考 `search-quality-annotation-template.json`。正式数据必须包含真实 query、候选 siteId、两名独立标注和仲裁状态。模板中的空字段不是有效样本。

## 8.1 真实金标 JSONL 导入校验器

新增 `scripts/import-search-golden.mts`，每行一条 `navhub-search-golden-v1` 记录。必需字段：

- `sampleId`：去标识化样本 ID，整个文件唯一。
- `query`：来自真实搜索遥测、已脱敏的查询文本；必须由数据负责人确认 `privacyReviewed=true` 与 `queryRedacted=true`。
- `sourceType`：必须为 `search_telemetry`；合成查询、模型生成查询不能冒充真实样本。
- `sampledAt`、`snapshotAt`：抽样时间与候选结果快照时间。
- `hits`：冻结快照中的站点 ID 与严格递增 rank。
- `judgments`：每个 hit 必须由两名不同标注员独立判断，包含证据 URL、0–3 等级或 `unjudgeable` 状态及理由码。
- 两人结论不同必须由第三名仲裁员给出最终等级/不可判断状态；不能把不可判断自动记为 0。

正式导入命令：

```bash
node scripts/import-search-golden.mts private/search-golden.jsonl scripts/fixtures/search-eval.real-golden.json
node scripts/search-eval.mts scripts/fixtures/search-eval.real-golden.json --k 10 --json
```

导入器默认要求至少 100 条有效样本；`--allow-below-target` 仅用于开发预览，输出会明确标记未达标。输出 fixture 的 `query` 字段被替换为 `sampleId`，不包含原始查询文本；原始脱敏查询与标注记录应保存在受控数据目录，不要提交到公开仓库。导入器只验证人工记录，不调用 LLM、不推断相关性、不伪造样本。输出文件采用独占创建，避免意外覆盖已有金标资产。

## 9. 本轮禁止事项

- 不用 LLM 自动生成 relevance 作为最终金标。
- 不把一次 HTTP 200 当作高相关或高质量。
- 不把 WAF、403、超时直接当作站点死亡。
- 不将用户身份或可识别个人信息写入 golden fixtures。
- 不因离线指标变好就直接更改生产排序；必须经过分层评测和人工审批。
