# 异步恢复方案 · 深度审阅与后续行动（2026-10-25）

> 审阅对象：`docs/ASYNC-RESTORE-DESIGN.md` 及其落地代码（`apps/api/src/routes/backup.ts`、
> `apps/api/src/jobs.ts`、`packages/store/src/repository/sites.ts`）。
>
> **一句话结论**：方案结构是标准的 Asynchronous Request-Reply 模式，落地完整、可用；
> 但它最核心的安全论证——「幂等性可以兜住分片的原子性」——**在任务重试这条路径上不成立**，
> 会产生重复站点行。这不是理论风险：`MAX_JOB_ATTEMPTS = 3` 且 `insertSitesBulk` 是裸
> `INSERT INTO sites`，`sites.url` 上没有唯一约束，所以重复写入既不会报错也不会被拦下。

## 2. 方案结构梳理

| 层 | 设计 | 落地 | 评价 |
|---|---|---|---|

## 3. 核心目标达成度

| 目标（§1.3） | 达成 | 证据 |
|---|---|---|
| 1. 不再占用 HTTP 请求时长 | ✅ | 请求内只做校验/算计划/写 staging；实测 1 万条预演 388ms |
| 2. 调用方能看到进度 | ✅ | `progress_done` / `progress_total` + 前端进度条 |
| 3. 失败可归因，**且不留半套数据** | ❌ | 与分片方案**直接矛盾**——分片的前提就是「失败时可能留下前几片」。见 §5 R1 |
| 4. 与同步端点共存 | ✅ | 同步端点未改，前端按阈值择一 |

> 目标 3 是文档里最危险的一句：它是选分片之前写下的，选了分片之后没有回头改。
> 后来者照这条目标验收，会把「留下前几片」判成 bug，或者反过来以为不该留下。

## 4. 关键假设逐条验证

| # | 假设（出处） | 结论 | 证据 |
|---|---|---|---|
| H1 | 幂等性可以兜住分片的原子性（§4.1） | **部分不成立** | 幂等只在**请求级**成立（重新提交会重跑 `planRestore` 过滤已存在 URL）；**任务重试级不成立**：`runBackupRestore` 从 `i=0` 重放冻结的 staging，`insertSitesBulk` 无 `ON CONFLICT`/去重，`sites` 无 url 唯一索引 |
| H2 | 校验廉价，可放请求内（§2.1） | 成立 | 实测预演 388ms @1.8MB。但 4MB 上限处未测，外推约 0.9s，仍可接受 |
| H3 | 单事务持锁 30s+，分片每片约 1.5 秒（§4.1 表） | 前半外推、后半**未实测** | 现有唯一数据点是「2100 条跨两片 9 秒」→ 单片约 4.5 秒，是文档值的 3 倍。分片大小从未做过 knee 测量 |
| H4 | 任务不会触发僵尸回收（40s ≪ 15min）（§4.3） | 本地成立，**条件外不成立** | `reapStaleJobs` 判 `updated_at < now-15min`。PG 远程/慢库下 5 万条完全可能超过 15 分钟，此时任务**仍在跑**却被回收重认领 → 两个 worker 并发写同一计划（代码注释自己提到过这个风险） |
| H5 | staging 目录在多实例下共享（§3） | 设计已声明，部署侧未保障 | 默认 `data/restore-staging` 是**相对路径**（相对进程 cwd），容器未挂卷即静默丢失 |
| H6 | jobs 补列走既有机制（§4.2） | 成立 | `COLUMN_ALTERS` 清单驱动，已改 DDL×2 + ALTERS，测试覆盖 |
| H7 | 条目上限 5 万（§2.1） | **实际封顶在别处** | 4MB `bodyLimit` 先触发：完整字段的备份约 3.5–4 万条就到 4MB。5 万条上限只在「字段压到最少」时才可达，是个形同虚设的上界 |
| H8 | `pruneJobs` 不会误删 running | 成立 | 只删 `done/failed/cancelled`，且手动触发 |
| H9 | 前端刷新后能接回（§7） | 成立 | sessionStorage + TTL；**多标签页会各自轮询同一 job** |
| H10 | 恢复保留 `enabled`（停用态） | 成立 | 已由并行会话修复并入库 |
| H11 | 预演与真写用同一套判定（§2.1） | 成立 | 共用 `planRestore`，但**两处 URL 归一化口径不同**，见 R5 |
| H12 | 语义索引由 reindex 补齐 | 成立 | 恢复后入队 `reindex`；只在 staged>0 时入队（可接受） |

## 5. 风险清单

### P0

**R1 · 任务重试会重放已提交的分片，产生重复站点行**

- 触发：任务在第 N 片抛错 / 超时 / 进程被杀 → `status=retrying`（`MAX_JOB_ATTEMPTS=3`，退避 1/2/4 分钟）→ 重新认领 → 从 `i=0` 重放。
- 后果：前 N-1 片再插一遍。`sites.url` 无唯一约束 → 不报错 → 库里出现多条同 URL 站点，**用户在导航页看到重复卡片**，且此后任何恢复都会把它们判成「已存在」而永久保留。
- 证据：`apps/api/src/jobs.ts:1025` 起 `for (let i = 0; ...)`；`repository/sites.ts` 的 `INSERT INTO sites (` 无冲突处理；`driver.ts` 无 `sites(url)` 唯一索引。

**R2 · 僵尸回收 + 重放 → 并发写**（H4 与 R1 耦合）

- 触发：任务超过 15 分钟仍在跑 → `reapStaleJobs` 认为它死了 → 另一个 worker 认领同一 job。
- 后果：两组分片**同时**写入；叠加 R1 的重放，重复量翻倍，且两组写入互相干扰。
- 这是「分片」+「无幂等」+「无并发守卫」三件事叠出来的，任何一件补上都能降级。

**R3 · 文档与代码 8 处不符，其中一处是目标级矛盾**

最危险的已列在 §3（目标 3）。其余：`§1.4` 声明「不改前端」但前端已做；`§6` 的 `asyncRecommended` 从未实现（实际是前端按阈值切）；`§7` 描述的是旧设想（2 秒轮询/跳转 sitelist），实际是 1.5 秒/转后台/不跳转；`§2.1` 的 `stagedBytes` 与 `?dryRun=false` 参数都不存在；`§4` 代码签名已变（`(payload, jobId)`）；`§8` 第 6 条仍写 `completed`、第 7 条仍写「非发起者 404」（实际是 admin scope 拦截）。

### P1

**R4 · 后端没有并发守卫**：只在前端禁用了文件输入。两个 admin（或绕过 UI 的 curl）同时提交 → 交错写入。
**R5 · 两处 URL 归一化口径不一致**：`planRestore` 用 `replace(/\/+$/,"").toLowerCase()`，`findExistingSiteUrls` 用 `canonicalizeUrl()`（还会探测带/不带斜杠的两种形态）。同一 URL 在两处可能得出不同的「是否已存在」。
**R6 · 契约缺 `Location` 与 `Retry-After`**：行业标准（Microsoft API 指南、OpenAPI 异步模式）要求 202 带 `Location` 指向 status 资源，并用 `Retry-After` 让服务端指挥轮询节奏。当前只有 body 里的 `statusUrl`，客户端节奏写死 1.5 秒。
**R7 · staging 被 sweep 删掉后，job 仍报 `retryable: true`**：超过 24 小时的失败任务重跑时读不到 staging → 必失败，但状态说「可重试」。
**R8 · 没有取消通道**：整库写操作一旦提交无法中止，只能等它跑完。

### P2

**R9 · 零增量时仍创建任务**：备份里全部条目都已存在 → `total=0` → 前端进度文案停在「正在准备恢复计划…」，然后才报「成功恢复 0 个站点」。
**R10 · 前端轮询无退避、无上限**：长任务（PG 下可能十几分钟）会持续每 1.5 秒打一次。
**R11 · 分片大小 2000 是拍的，没做过基准**（见 H3）。
**R12 · staging 默认相对路径**（H5），容器部署易踩。

## 6. 可行性评估

- **已实现部分的可行性：高**。契约、载荷、进度、前端都跑通并有测试；异步化确实解决了原本的问题（请求时长与数据量解耦）。
- **薄弱环节的共性**：方案把「正确性」押在了**幂等**上，而幂等只在**一次请求的边界内**成立；一旦跨越「任务重试 / 并发 / 时间窗口」这三个边界，它就失效了。三处薄弱（R1/R2/R4）本质都是同一件事：**缺少一个跨边界的、写入时的幂等或互斥保证**。
- 好消息：所需的原语仓库里**已经存在**（`findExistingSiteUrls(repo, urls)`、`jobs` 表查询、`progress_done`），修复不需要新建机制。

## 8. 建议执行顺序

```
第一批（同一提交，互不依赖，约 2 小时）
  A1 分片写前去重   ──┐
  A2 后端并发守卫   ──┼── 三者独立，可并行改不同文件
  A3 文档修订       ──┘   （A3 会把 A1 的语义变化写回设计文档）

第二批（依赖第一批的稳定，约 1 小时）
  A4 断点续跑  ← 建议 A1 已合入（否则续跑仍可能重插）
  A5 归一化统一 ← 独立，但与 A1 同文件区，建议在 A1 之后改以免冲突
  A7 sweep 保护 ← 独立

第三批（体验与契约完善，约 1.5 小时）
  A6 Location/Retry-After ──→ A9 前端退避（A9 依赖 A6）
  A8 零增量直返

第四批（可选）
  A10 取消通道（需先确认 JobRunner 改造范围）
  A11 分片基准（需要先有 5 万条基准脚本）
```

**为什么 A1 要排在最前**：它同时修掉 R1（重试重放）、R3 的一部分（TOCTOU 窗口）、并给 R2 兜底。改动量只有十几行，但它是整个方案里唯一「正确性依赖一个未成立的假设」的地方。

## 9. 明确不建议做

| 不做 | 理由 |
|---|---|
| 给 `sites.url` 加唯一索引 | 库里存在软删除的同 URL 行，加索引会让恢复直接撞约束失败，也会破坏 `findExistingSiteUrls` 只认 `deleted_at IS NULL` 的既有语义。用写入时过滤替代（A1） |
| 改回单事务求原子性 | 单事务持写锁数十秒是可用性问题，且大事务回滚成本高。分片方向是对的，缺的是幂等 |
| 断点续传（跨进程续跑未提交片） | 恢复本身能在几十秒内重跑完，续传的复杂度不值。A4 的「从已提交片之后继续」已经是够用的折中 |
| 引入 SSE / WebSocket 推进度 | 轮询在这个场景（分钟级、单一调用方）够用；A6 的 `Retry-After` 已能解决节奏问题。引 SSE 要动 BFF 的压缩与代理配置（记得 `/api/hub/*` 会解压重发），收益不抵 |
