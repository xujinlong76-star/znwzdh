## 1. 安全类

### 1.1 SSRF：IPv6 变体绕过（高危 · 已修）

**问题**
`packages/ai/src/ssrf.ts` 的 `isBlockedIpv6` 用**字符串前缀**判断危险网段，只覆盖
`::ffff:<点分>`、`::ffff:<hex>:<hex>` 等少数写法。实测以下写法全部返回 `false`（放行）：

```
0:0:0:0:0:ffff:127.0.0.1               # ::ffff:127.0.0.1 的完全展开写法
0000:0000:0000:0000:0000:ffff:7f00:0001
::127.0.0.1 / ::7f00:1                 # IPv4 兼容地址（Linux 上可路由到回环）
64:ff9b::127.0.0.1                     # NAT64 内嵌 v4
fe90::1 / fea0::1 / febf::1            # fe80::/10 只拦了 fe80 前缀
```

同一地址有无数种合法书写形式，前缀匹配必然漏。在 Linux/Docker（本项目实际部署目标）上，
`::7f00:1` 会被解析为 IPv4-compatible 回环地址，构成真实可利用的 SSRF。

**修复**
新增 `ipv6ToBytes()` 把地址真解析成 16 字节（处理 `::` 压缩、末尾点分 v4、zone id），
再按字节判定：IPv4-mapped `::ffff:0:0/96`、IPv4-compatible `::/96`、NAT64 `64:ff9b::/96`、
6to4 `2002::/16`、Teredo `2001::/32`、`fe80::/10` 全段、`fc00::/7`、`ff00::/8`、`2001:db8::/32`。
解析失败一律 fail-closed。

顺带修两处同源问题：
- `guardedFetch` 的 catch 把 `SsrfBlockedError` 包装成普通 `Error`，调用方的 `instanceof`
  判定失效（被拦截会被当成 500 网络错误）。
- https 的二次 DNS 校验用 `.catch(() => undefined)`，**连"解析到内网"也一并吞掉**，
  等于重绑定防护没做。改为只吞瞬态失败、放行 `SsrfBlockedError`。

**验证**：15 个危险地址全部拦截、5 个公网地址正常放行；`ai.test.ts` 新增 3 组用例。

### 1.2 Next 侧 SSRF 副本更弱（高危 · 已修）

`apps/web/src/lib/ssrf-guard.ts` 是独立副本（不依赖 workspace 包），其 `isBlockedIp`
只判 `::1`/`::`/`fc`/`fd`/`fe80` 前缀与点分 mapped 形式，比 API 侧还弱。已对齐同一套
字节级判定，并补齐 IPv4 保留段（198.51.100/24、203.0.113/24、192.88.99/24 等）。

> 设计备注：两份实现长期并存是结构性隐患。受限于 `apps/web` 是 vendored 上游底座、
> 不能直接引 workspace 包，本次保持"两份但同源同行为"，并在两侧都加了测试。

### 1.3 无界响应体读取（中危 DoS · 已修）

`apps/web-overlay/src/app/api/website-metadata/route.ts` 只校验 `content-length` 响应头，
随后用 `response.text()` / `arrayBuffer()` 一次性读入内存。分块传输可以不带该头，
或给一个远小于实际体量的假值 —— 攻击者可控的 URL 就能让服务端把任意大小的响应读进内存。

**修复**：新增 `readBodyLimited` / `readTextLimited`（流式读取、按实际字节截断并 `cancel()`），
替换 HTML 抓取与图标下载两处调用点。

## 2. 数据一致性 / 并发类

### 2.1 事务并发导致数据丢失（严重 · 已修）

**问题**
`Repository.withTransaction` 用实例字段 `txDepth` 判断"是否已在事务中"。该字段**跨请求共享**：

```
请求 A: withTransaction → txDepth=1 → BEGIN → 写入 A → await ...（挂住）
请求 B: withTransaction → 看到 txDepth>0 → 直接执行 action()（没有 BEGIN）
请求 A: 抛错 → ROLLBACK  ← B 的写入被一起回滚，而 B 早已返回"成功"
```

`withTransaction` 有 19 个调用点，其中 `routes/sites.ts`、`storage.ts` 是请求级入口，
生产并发下必然触发。

**复现**：`packages/store/test/transaction-concurrency.test.ts` 用两个交错事务稳定复现
（B 提交后查不到）。

**修复**：`AsyncLocalStorage` 判"同一条异步调用链内的真嵌套"，跨请求不再互相看见；
再用 `txLock` 把事务串行化（SQLite 单连接、PG 侧会临时替换 `db.pg`，交错执行本来就不安全）。

**影响**：写事务从"并发但错误"变为"串行但正确"。SQLite 本来单写者，无损失；
PostgreSQL 下写事务吞吐会下降，换取原子性 —— 建议后续把 PG 的 `db.pg` 临时替换
改成显式传 client，再放开并发。

### 2.2 管理页孤儿（低危 · 已修）

`/admin/plugin-health` 页面存在但全站无入口（`admin-nav.test.ts` 因此红）。
已在侧边栏「插件市场」下补 subItems（插件审核 / 网址体检）。

### 2.3 检索耗时串号（低危 · 已修）

`SearchEngine` 是单例，`lastTimings` 是实例字段。并发搜索时 A 的请求会读到 B 的通道耗时，
`/metrics` 的通道画像失真。改为 `runChannels` 返回 timings，随 `result.channelTimings` 下发；
路由改读返回值，`getLastTimings()` 仅保留兼容。

## 4. 已查证排除（不是问题）

- **SQL 注入**：`repository/plugins.ts` 的 `ORDER BY ${order}` 是固定字符串白名单
  （`popular/stars/rating/...`）；`LIMIT` 插值均为 `Math.min/max` 归一后的数字；其余查询全部参数化。
- **鉴权**：`hashToken` 用 sha256、比对用 `timingSafeEqual`、scope 分级 `admin ⊇ write ⊇ read` 正确；
  非法 scope 静默丢弃（不放大权限）。
- **LinUCB 数值**：`invertMatrix` 带部分主元 + Tikhonov 兜底；`A` 始终正定，奇异分支实际不可达。
- **搜索防抖 / 定时器**：`spotlight-modal` 与 `search-palette` 的 `setTimeout`、`AbortController`
  均有 cleanup，未发现卸载后 setState。
- **`parseInt` 无基数**：13 处均为显式 16 进制。
- **`.sort()` 无比较器**：命中的都是字符串数组（字典序即预期）或测试断言。

## 5. 已知未修（低危 · 建议后续处理）

1. `search.ts` 的 `alt_labels LIKE ?` 未转义 `%` / `_`：含这两个字符的查询会多召回同义词。
   只读、影响面小；修复需统一引入 `escapeLike` 约定（仓库当前无此约定），改动面大于收益。
2. `isBlockedIpv4` 中 `a===192 && b===0` 注释写 `/24`、实际拦 `/16`（192.0.1.x 等被过度拦截）。
   方向是"宁可多拦"，无安全风险，仅注释与实现不一致。
3. SSRF 双副本：行为已对齐，但仍是两份代码，未来易再次漂移。
   建议在 vendor 流程里把 `ssrf-guard.ts` 纳入"单向生成 + 校验"。
