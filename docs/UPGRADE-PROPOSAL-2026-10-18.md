# NavHub 网站升级建议方案

> 基线：2026-10-18 工作区实况（778 个文件 / 155,150 行），前端生产构建实测 + 中枢接口实测 + 源码核查。
> 与既有文档的关系：`docs/UPGRADE-RECOMMENDATIONS-2026-10-16.md` 的 25 项（后端与基建）已执行完毕，**本方案不重复**那些内容，专注网站侧的界面、体验、性能、功能与安全。
> 所有数字均标注来源；标「估算」的为基于实测的推算，落地前需用基线数据校准。

## 一、执行摘要

**三个判断**

1. **能力已经过剩，感知仍然不足。** 五路检索、Bento 工作台、0-RTT 微工具、知识图谱都做完了，但首屏 JS 约 1.0 MB（路由包 685 KB）、首页每次请求 3 次存储读、19 张图片没有尺寸约束——用户先感受到的是「重」和「慢」，而不是「强」。
2. **最强的资产是「搜索 + 工作台」，最弱的一环是「第一次打开」。** 新用户落地后没有引导：不知道可以导入书签、不知道有工作台模式、不知道 `⌘K`。功能发现性靠用户自己摸索。
3. **安全纵深在后端已经很好，短板在浏览器侧。** CSP 默认关闭、next-auth 仍是 v5 beta、管理端没有二次验证。这三项都不是「有没有做」，而是「默认值不安全」。

**P0 五件事（一周内，全部低风险）**

| # | 动作 | 一句话收益 |
| :--- | :--- | :--- |
| P0-1 | 建立性能与体验基线（Web Vitals + Server-Timing + Lighthouse CI） | 后续每项优化都可验证，避免拍脑袋 |
| P0-2 | 首页数据链路去重（3 次存储读 → 2 次） | 每访问少一次跨进程往返 |
| P0-3 | 快照短缓存 + 写路径版本失效 | 命中时 TTFB 降 40–60%（估算），中枢 QPS 降一个量级 |
| P0-4 | 图片管线统一（19 处裸 `<img>` → 带尺寸 + 懒加载） | 消除 CLS，首屏图片请求可控 |
| P0-5 | 可访问性快赢（focus-visible / aria-live / 对比度） | 键盘与读屏用户从「能用」到「好用」 |

## 二、基线：实测数据

### 2.1 前端构建产物（`next build` 实跑，`NEXT_DIST_DIR=.next-analysis`）

| 指标 | 实测值 | 说明 |
| :--- | :--- | :--- |
| 首页路由初始 JS | **685 KB**（16 个 chunk，未压缩） | 页面 chunk 133 KB + 两个公共 chunk 169/171 KB + 12 个小 chunk |
| 首屏实际 JS（含运行时） | **≈1.0 MB**（未压缩） | 路由清单 685 KB + framework 214 KB + main 129 KB（HTML 直接注入，不计入路由 manifest） |
| 首页关联全部 JS | 903 KB（26 个 chunk） | 含异步分包（工作台、图表等） |
| 全站共享 JS | 103 KB | Next 构建报告值（gzip 前） |
| `/hot` 初始 JS | 515 KB | 榜单页 |
| `/algorithms` 初始 JS | 518 KB | 算法实验室 |
| `/admin/sitelist` 初始 JS | 454 KB | 后台最大页面 |
| 最大单 chunk | 462 KB（异步） | 编辑器类重依赖，已按需加载 |
| 静态资源总量 | 4.0 MB | `.next/static` |

> 参照：同规模内容型站点首屏 JS 通常在 150–250 KB（未压缩口径约 400–600 KB）。当前约 1.0 MB，**gzip 后约 280–320 KB（估算）**——对导航站偏重，但仍有明确压缩空间，不是「重写」级别的。
> 口径说明：Next 的 framework/main 由 HTML 直接注入、不在路由 manifest 内，因此单看 manifest 会低估约 340 KB；`polyfills` 仅对旧浏览器下发，不计入现代浏览器首屏。

### 2.2 中枢接口（本地实跑，SQLite，50 站点 / 5 分类 / 77 标签）

| 接口 | 耗时 | 响应体 | 备注 |
| :--- | ---: | ---: | :--- |
| `GET /api/health` | 28 ms | — | 冷启动后首次 |
| `GET /api/storage`（快照） | **10–20 ms** | 28 KB | 每次全量重建，无缓存 |
| `GET /api/search?q=代码` | 7–38 ms | — | 语义通道未预热时跳过 |
| `GET /api/sites?limit=100` | 6 ms | — | — |

**关键结论**：在 50 站点规模下，快照重建不是瓶颈；但它是**唯一没有缓存的全量操作**，成本随站点数线性增长，且首页 `force-dynamic` 让每次访问都触发。

### 2.3 代码侧证据

| 项 | 实测 | 影响 |
| :--- | :--- | :--- |
| 客户端组件 | 99 / 204 个文件带 `"use client"` | 首屏水合面积大 |
| 路由级 `loading.tsx` / `error.tsx` | 4 个（全局 + admin） | 切页白屏、错误无局部兜底 |
| 裸 `<img>` vs `next/image` | 19 : 2 | CLS、无自动优化 |
| `aria-*` / `role=` / `focus-visible` | 139 / 26 / **6** | 焦点可见性覆盖不足 |
| 首页数据读取 | 每请求 3 次（layout 1 + page 2），2 个唯一文件 | 重复往返 |
| 缓存策略 | `/api/storage` 无 `cache` 配置 → `no-store`；适配器 `cache: "no-store"` | 三层全关 |
| 健康巡检 | 50 站点中 **15 个 broken**（含 kubernetes.io、figma.com、npmjs.com） | 误判率高，前台可能误标 |

> 坏链误判说明：本机网络受限会放大该问题，但**「单次探测即判定 + 无重试/多 UA」的判定逻辑**在生产同样脆弱，且 15 个里有 8 个是明显可用的知名站点，足以说明需要治理。

## 四、建议清单

### P0 — 本周（1–5 人日，低风险）

#### P0-1 建立性能与体验基线（已实现，Lighthouse CI 以构建期预算替代）

- **现状**：有 GA4（`layout.tsx:130`）但只做访问统计；无 Web Vitals 上报、无 `Server-Timing`、CI 无 Lighthouse。
- **动作**：① 接入 `web-vitals`（LCP/INP/CLS/TTFB）随 GA4 或自建 `/api/events` 上报；② 中枢关键路由加 `Server-Timing: db;dur=…, snap;dur=…`；③ CI 增加 Lighthouse CI（首页 + `/hot` + `/site/[id]` 三条，预算：LCP<2.5s、JS<500KB）。
- **预期收益**：让 P1 的每项优化都有前后对比；避免「感觉快了」式验收。**这是唯一一项「不直接改善体验但决定其余项是否可信」的投入。**
- **实施考量**：1 人日；需确认 GA4 是否已配置（未配置则先落到自建事件表，避免引入新三方）；Lighthouse CI 在容器内跑需固定 Chrome 版本。
- **落地情况**：Server-Timing、RUM（`NEXT_PUBLIC_RUM=1` 开启，上报 `/api/vitals`）、`pnpm check:bundle` 已实现；未引入 Lighthouse CI——它需要跑服务 + Chrome，在容器 CI 里慢且易误报，改用构建产物上的确定性预算检查。
- **验收**：能查到首页 p75 LCP/INP/CLS；`pnpm check:bundle` 在预算超标时退出 1。

#### P0-2 首页数据链路去重（复核后改判：已存在，本轮不重复实现）

- **复核结论**：`lib/github.ts` **已有 2.5 秒内存微缓存**（`contentCache` + 写操作 `invalidateContentCache`），因此 layout 的 `generateMetadata` 与 page 的 `getData` 对同一个 `site.json` 的两次读取中，第二次命中缓存——实际唯一读取是 **2 次**（navigation + site），不是 3 次。
- **动作**：不再新增第二层前端缓存（双层失效只会让「保存后刷新」更难保证），改为在**中枢侧**做快照缓存（P0-3），前端微缓存继续承担「同一次渲染内的并发突发吸收」。
- **预期收益**：与 P0-3 合并计算；持续流量下不再每 2.5 秒回源重建一次快照。
- **实施考量**：若将来前端 TTL 需要调整，务必与中枢 TTL 一起看——前端 TTL 必须 ≤ 中枢 TTL，否则会出现「中枢已更新、前端仍返回旧值」。
- **验收**：首页连续访问时，中枢 `/api/storage` 的实际重建次数显著低于访问次数（见 P0-3 验收）。

#### P0-3 快照短缓存 + 三重失效（已实现）

- **现状**：`/api/storage` GET 无 `cache` 配置 → 全局 `no-store`；`buildNavigationData` 每次全量查库 + 组装（`storage.ts:73`）；首页 `force-dynamic`。
- **动作（已落地）**：
  1. `apps/api/src/storage.ts` 新增 `readNavigationSnapshot()`：30s 进程内缓存（`NAVHUB_SNAPSHOT_TTL_MS`，0=关闭）；
  2. **三重失效**：① `server.ts` 的 `onResponse` 对 `/api/sites|categories|storage|enrich|submissions|trash|collections|relations|tags|facets|taxonomy` 的成功写请求统一失效；② `writeStoragePath` 内部再显式失效一次；③ **库指纹**（sites/categories 的 `COUNT(*) + MAX(updated_at)` + `site_tags` 计数）每次读取比对，覆盖「后台任务/脚本绕过 HTTP 直接写库」的场景；
  3. 路由加 `cache: { maxAge: 0, etag: true }`：响应带 `ETag` 与 `private, no-cache`，条件请求返回 **304**。
- **预期收益**：命中时省掉一次全量查库 + 组装；站点数越大收益越明显（50 站约 10–20ms，1000 站预计数百毫秒）；带宽因 304 显著下降。
- **实施考量**：缓存是进程内的，standard 多实例下各实例独立，最长滞后一个 TTL（已写入 `.env.example` 注释）；指纹查询在 PG 十万级行上会退化为顺序扫描，如成瓶颈可调小 TTL 或改版本号方案。
- **验收（已自动化）**：`apps/api/test/snapshot-cache.test.ts` 4 例——缓存命中、直写库后失效、HTTP 写后失效、ETag 304；连同 `navigation-snapshot.test.ts` 与 `api.test.ts` 共 116 例通过。

#### P0-4 图片管线统一

- **现状**：19 处裸 `<img>`，仅 2 处 `next/image`；站点图标走 `SiteFavicon`（含确定性渐变兜底），但尺寸/懒加载不统一。
- **动作**：① 所有站点图标收敛到 `SiteFavicon`；② 非图标图片统一 `next/image` 或显式 `width/height` + `loading="lazy"` + `decoding="async"`；③ 首屏 Logo/Hero 图加 `priority`；④ `NAVHUB_IMAGE_HOSTS` 已在 `next.config.js` 支持，生产建议收紧。
- **预期收益**：CLS 从当前不可控降到 <0.1；首屏非关键图片请求延后，LCP 更稳。
- **实施考量**：1 人日；`next/image` 对任意域名图标需走 `remotePatterns`，favicon 场景建议继续用 `/api/favicon` 代理（已有）以避免放开通配。
- **验收**：Lighthouse CLS <0.1；页面中裸 `<img>` 仅剩装饰性内联 SVG。

#### P0-5 可访问性快赢

- **现状**：已有 skip-link、reduced-motion、部分 aria（139 处），但 `focus-visible` 仅 6 处；图标按钮大量依赖 `title`。
- **动作**：① 在 `globals.css` 增加全局 `:focus-visible` ring（token 化，暗色适配）；② 搜索面板结果变化加 `aria-live="polite"` 播报「找到 N 条」；③ 所有纯图标按钮补 `aria-label`；④ 用 axe 扫首页/搜索/收藏/后台四页，修 critical。
- **预期收益**：键盘用户可完整走通「搜索 → 选择 → 打开」；读屏用户能感知结果更新；接近 WCAG 2.1 AA。
- **实施考量**：1 人日；全局 focus ring 可能影响既有视觉，需与设计 token 一起调；避免 `outline: none` 的历史写法。
- **验收**：axe critical = 0；Tab 走查无「焦点丢失」；搜索有结果时读屏播报。

### P1 — 2–4 周（中风险，需排期）

#### P1-1 首屏分包治理（已执行一轮，目标修正）

- **现状**：首页路由初始 685 KB / 16 chunk（含运行时约 1.0 MB）。工作台（`ModularCanvas`）、Hero 微组件、图表类组件参与首屏依赖图。
- **动作**：① `next/dynamic` 懒加载 `ModularCanvas`、`HomeHeroDeck`、`AlgorithmLab`、`EcosystemGraph`（`ssr:false` 仅对纯客户端可视化）；② 检视 `lucide-react` 是否按需导入（`nav-icon.tsx` 已做映射，需确认无 `import *`）；③ 把 `recharts` 限定在图表路由；④ 目标：首页初始 JS **685 → ≤480 KB**。
- **预期收益**：路由初始 JS 685 → ≤480 KB（-30%），含运行时约 1.0 MB → 约 0.8 MB；移动端 4G 下可交互时间预计提前 300–600ms（估算）。
- **实施考量**：3–5 人日；懒加载会引入一次额外请求与 loading 态，必须配骨架屏（P1-3）；工作台是首页默认视图之一，不能整块延后到点击后——建议按 `viewMode` 条件加载。
- **已落地**：`HomeDIYToolbar`（1,365 行）、`BatchOperationDock`、搜索里的三张富卡片（投机意图/技术对比/架构配方）改为 `next/dynamic` 客户端懒加载；首页路由初始 JS **685 → 637 KB（-48 KB，-7%）**。
- **目标修正**：685 KB 中约 344 KB 是 React/ReactDOM 运行时（两个 chunk 各 169/171 KB），不可压缩。因此「≤480 KB」在不动框架的前提下不可达；修正为**应用代码 ≤600 KB**，并在 `scripts/bundle-budget.json` 里用 669 KB 阈值防回退。
- **剩余空间**：`search-palette` 的 cmdk（56 KB）与 `navigation-content` 的内联逻辑（133 KB）。前者要保留方向键导航，替换需重写键盘模型；后者属 P1-2 拆分范畴。
- **验收**：`pnpm check:bundle` 首页 ≤669 KB（当前 637 KB）；LCP 不回退。

#### P1-2 巨型组件拆分

- **现状**：`algorithm-lab.tsx` 2,212 行、`admin/sitelist/page.tsx` 2,063 行、`home-diy-toolbar.tsx` 1,365 行、`navigation-content.tsx` 1,212 行、`use-home-diy.ts` 1,212 行。
- **动作**：按既有成功范式拆四层：**容器（取数）/ 视图（渲染）/ hooks（状态）/ 纯函数（可单测）**。优先 `navigation-content`（首页核心路径）与 `use-home-diy`（状态最复杂），其次 `sitelist`，最后 `algorithm-lab`（低流量、可延后）。
- **预期收益**：单文件改动风险下降；纯函数可被 vitest 覆盖（当前前端几乎无组件测试）；为 P1-1 的条件加载创造条件。
- **实施考量**：5–8 人日；纯机械拆分收益有限，**必须同时补测试**，否则只是把风险从「大文件」转移到「多文件」；建议每拆一个跑一次 `verify:all`。
- **验收**：四个文件均 <600 行；新增纯函数单测 ≥30 例；E2E 全绿。

#### P1-3 路由级加载与错误边界

- **现状**：仅 `app/loading.tsx`、`app/error.tsx`、`app/not-found.tsx`、`admin/loading.tsx` 四个边界；`/site/[id]`、`/hot`、`/favorites`、`/admin/*` 切页时无局部兜底。
- **动作**：为 12 条主要路由补 `loading.tsx`（骨架屏对齐真实布局）与 `error.tsx`（复用 `lib/error-report` 的分类文案 + 重试）；后台按域补 3 个。
- **预期收益**：切页不再白屏；单页崩溃不拖垮整站；错误可行动（当前全局 error 已做好，局部缺失）。
- **实施考量**：2 人日；骨架屏必须与真实布局同构，否则会「跳一下」；错误边界要避免吞掉 404。
- **验收**：弱网（Slow 3G）下切页有骨架；人为抛错时局部降级且可重试。

#### P1-4 设计系统 2.0

- **现状**：133 个 CSS 变量，暗色/密度/圆角/阴影齐全；但 token 未分层，组件状态（hover/active/disabled/loading/focus）无成文规范，空态以文字为主。
- **动作**：① token 三层化：**原始值 → 语义（surface/text/border/accent）→ 组件（card/button/input）**；② 输出「组件状态矩阵」一页纸（含暗色）；③ 空态统一为「图标 + 一句解释 + 一个主行动」的 `<EmptyState>`；④ 动效时长/缓动统一 token，保留 reduced-motion 覆盖。
- **预期收益**：新页面开发速度提升（复用而非重画）；暗色模式一致性提升；空态从「死路」变成「下一步」。
- **实施考量**：5 人日；**不要一次性替换全部类名**，先建 token 与 3 个样板组件（Card/Button/EmptyState），再逐页迁移；迁移期两套并存需约定边界。
- **验收**：新增页面 90% 样式来自 token；暗色下无硬编码色值；空态组件覆盖主要 8 个列表页。

#### P1-5 首访引导（Onboarding）

- **现状**：无引导。新用户看到的是「已配置好的导航站」，不知道：可以导入书签、可以切工作台、`⌘K` 能搜、可以钉常用。
- **动作**：三步轻引导（可跳过、只出现一次）：① 导入书签（指向 `/import`，展示支持 Chrome/OneTab/Markdown）；② 选工作区（`WorkspaceFilter` 已有，引导点一下）；③ 钉 3 个常用站点（写入工作台）。用 `localStorage` 记完成态，设置页可重看。
- **预期收益**：直接作用于激活率——预计「首日导入或收藏」转化提升 15–25%（估算，需 A/B 校准）；工作台使用率提升。
- **实施考量**：3 人日；**不要做遮罩式强制 tour**（导航站用户极反感），用非阻塞的卡片/气泡；必须可跳过且不重复弹。
- **验收**：新用户首访完成率、首日收藏/导入率对比基线。

#### P1-6 坏链治理

- **现状**：50 站点中 15 个被标 `broken`，含 kubernetes.io、figma.com、npmjs.com 等明显可用站点；前台仅搜索面板显示坏链标记（`search-palette.tsx:687`），卡片不显示。
- **动作**：① 判定改多信号：状态码 + 响应体特征（软 404/停放页，已有 `health-sentinel` 能力）+ 连续 N 次失败（建议 3 次、间隔 ≥6h）才置 `broken`；② 探测加超时与 UA 轮换，区分「网络不可达」与「站点故障」；③ 前台：卡片显示弱提示（灰点 + tooltip），不显示「已失效」硬结论；④ 详情页给「查看存档（Wayback）」与「换一个」入口（能力已有）。
- **预期收益**：误判率从当前 30% 降到 <5%（估算）；减少用户被错误标记劝退；坏链自愈能力真正可用。
- **实施考量**：3–4 人日；需要一次存量数据修正（把当前 15 个重跑）；探测频率与目标站压力要平衡（建议单站每天 1 次、失败后 6h 重试）。
- **验收**：抽样 100 站点人工核对，误判 <5%；前台不再出现「健康站点被标失效」。

### P2 — 1–2 个月（需立项）

#### P2-1 分享体系：从长链到落地页

- **现状**：DIY 分享是 `#diy=<base64>` 长链，无服务端存储、无 OG 预览；好友打开只能看到自己的站点数据 + 布局。
- **动作**：① 新增 `POST /api/share` 生成短码（存布局 JSON + 过期时间）；② `GET /s/[code]` 落地页渲染「别人的桌面」预览 + 「一键应用」；③ 生成 OG 图（标题 + 分类数 + 强调色）；④ 收藏夹支持公开只读分享。
- **预期收益**：分享从「复制一坨 base64」变成一条可发朋友圈的短链；带来自然流量与回访。
- **实施考量**：5–8 人日；需考虑内容安全（分享内容审核/举报）、过期清理（复用 `retention`）、隐私（不含私人收藏）。
- **验收**：短链创建→打开→应用全链路 <3 步；OG 图正确渲染。

#### P2-2 多用户与团队空间

- **现状**：单租户；身份是 `userId`/`anonId` 字符串（有 HMAC 保护）；收藏/画像/金库按身份隔离，但站点库全局共享。
- **动作**：引入 `workspace_id`（DB 迁移 + 查询过滤 + 权限模型 owner/editor/viewer）；个人空间默认存在，团队空间可邀请；后台管理按空间隔离。
- **预期收益**：从「个人导航站」升级为「团队知识工作台」，是商业化与留存的关键一步。
- **实施考量**：10–15 人日；**这是数据模型级变更**，必须先补权限测试再迁移；注意 MCP token 的 scope 需要绑定 workspace；迁移期双读写兼容。
- **验收**：两个空间数据完全隔离；越权访问 403；MCP 工具按空间生效。

#### P2-3 PWA 与离线深化

- **现状**：有 `sw.js`（导航 network-first、静态 stale-while-revalidate）与 manifest；离线时仅回退首页壳。
- **动作**：① 离线缓存「最近访问的 50 个站点」快照（IndexedDB）；② 安装引导（首次访问 3 次后提示）；③ manifest 增加 `shortcuts`（搜索/收藏/工作台）；④ 离线时搜索走本地索引（`client-vector-search` 已有）。
- **预期收益**：地铁/弱网场景可用；桌面安装率提升，回访路径缩短。
- **实施考量**：3–5 人日；缓存版本与 `sw` 更新策略要谨慎（避免用户卡在旧版本）；离线数据需明确「只读」边界。
- **验收**：断网可打开首页与最近站点；更新后 24h 内所有客户端切到新版。

#### P2-4 浏览器侧安全加固

- **现状**：CSP 由 `NAVHUB_CSP=1` 手动开启且含 `unsafe-inline`/`unsafe-eval`；next-auth 为 v5 beta；管理端仅密码/Token。
- **动作**：① CSP 默认开启，改 **nonce + strict-dynamic**（Next 支持 `headers()` 注入 nonce，需移除 `unsafe-eval`，dev 环境放宽）；② next-auth 评估迁移（Better Auth 或 4.x LTS），GitHub token 出进程内存；③ 管理端加 TOTP 二次验证 + 登录失败锁定（5 次/15 分钟）；④ 安全响应头补 `Cross-Origin-Opener-Policy`。
- **预期收益**：XSS 攻击面显著收窄（CSP 从「关」到「enforce」）；账号接管风险下降；满足企业采购的安全问卷。
- **实施考量**：CSP 3 人日（**必须先在 report-only 跑一周**，收集违规再 enforce）；next-auth 迁移 5–8 人日（登录全链路回归）；2FA 5 人日（含恢复码）。
- **验收**：CSP report-only 违规 <5 条/天后再 enforce；登录 E2E 全绿；2FA 开启率可统计。

#### P2-5 前端错误闭环（已落地）

- **现状**：`lib/error-report.ts` 已把崩溃分类（分块/网络/水合/存储满/运行时），但只用于展示，不上报。
- **动作**：错误边界捕获后上报（脱敏：不含 URL query 与用户内容），与中枢 `events` 表打通；配一个「前端错误率」看板。
- **预期收益**：发版后的白屏/分块错误可在分钟级发现，而不是等用户反馈。
- **实施考量**：3 人日；注意采样率与隐私（不采集输入内容）；错误去重按 `kind + message + route`。
- **已落地（2026-10-18 第三轮）**：`lib/client-error-report.ts`（三个错误边界接入；FNV-1a 指纹，**只发 kind/指纹/pathname/digest**，原文与 query 不出浏览器，默认关）+ `POST /api/errors`（白名单 + 带 query 的 path 400）+ 进程内指纹去重聚合 + events 表明细 + 后台「前端错误监控」卡片。
- **隐私取舍**：不上报错误原文（可能夹带用户输入）；指纹足够去重关联。
- **验收**：✅ 已达成——`client-errors.test.ts` 里人为制造的 ChunkLoadError 在聚合看板可见（count 累计、按 kind 计数）。

#### P2-6 搜索体验 2.0

- **现状**：已有多通道、建议、分面、纠错、最近搜索，体验已属上乘。
- **动作**：① 结果按「站点/标签/专题/工具」分组折叠；② 支持语法 `@分类 #标签`（后端已解析分面，前端补提示）；③ 历史可单条删除/一键清空；④ 结果项展示「为什么是它」（命中通道：精确/拼音/语义），把 LinUCB 的可解释性露出来。
- **预期收益**：从「能搜到」到「知道为什么搜到」；重度用户效率提升。
- **实施考量**：8–10 人日；分组会改变结果密度，需 A/B；「为什么是它」要注意别暴露内部权重细节。
- **验收**：搜索→点击转化率提升；零结果率下降。

## 七、反目标（明确不做）

1. **不重写上游 vendored 代码**——继续用 overlay 覆盖层机制，保持「上游可升级」这条生命线。
2. **不为 Lighthouse 分数牺牲检索质量**——语义通道该跑就跑，不用「延迟加载结果」换分数。
3. **不做强制遮罩式引导**——导航站用户对打断极度敏感，引导必须可跳过、只一次。
4. **不在没有基线前做「性能优化」**——先 P0-1，否则无法证明有效，也无法发现回退。
5. **不同时开多租户与分享两条大改**——两者都动数据模型与权限，串行推进。
6. **不引入新的状态库/ORM 解决现有问题**——当前问题在缓存、分包、组件粒度，不在状态管理。

## 八、风险与回滚

| 风险 | 触发场景 | 预案 |
| :--- | :--- | :--- |
| 快照缓存导致后台改完不生效 | 版本号失效漏了某条写路径 | 写路径统一走 `writeStoragePath` 收口；上线前补「保存后刷新」E2E |
| 懒加载导致首屏闪骨架 | 工作台是默认视图 | 按 `viewMode` 预判加载；骨架与真实布局同构 |
| CSP enforce 打挂页面 | 三方脚本/内联样式 | 先 report-only 一周；保留 `NAVHUB_CSP_MODE=report` 开关 |
| 组件拆分引入回归 | 状态提升/闭包依赖 | 每拆一个跑 `verify:all`；纯函数先补测试再搬 |
| 坏链重判把真坏站放过 | 连续失败阈值过高 | 阈值可配（`NAVHUB_HEALTH_FAIL_THRESHOLD`），后台可手动标记 |
| 多租户迁移丢数据 | 迁移脚本不可逆 | 迁移前 `backup.mjs`/`backup-pg.mjs`；双写兼容一版 |

**统一回滚**：每项独立分支、单文件隔离提交；前端改动可回滚到上一镜像（`docker/Dockerfile.web` 已固定上游 SHA）；数据类改动必须带 down 脚本。

## 九、一页结论

- **先做 5 件小事（一周）**：基线、去重、缓存、图片、可访问性——全部低风险，且为后续提供度量。
- **再做 6 件中事（三周）**：分包、拆分、边界、设计系统、引导、坏链——直接改善「第一次打开」和「每次打开」。
- **然后 6 件大事（两个月）**：分享、多租户、PWA、CSP/2FA、RUM、搜索 2.0——决定产品天花板。
- **判断标准只有一个**：新用户是否在 30 秒内完成「找到 → 收藏 → 下次还来」。
